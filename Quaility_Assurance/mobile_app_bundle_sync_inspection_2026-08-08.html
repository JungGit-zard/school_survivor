현재 확인된 단절 지점은 1단계의 최신 dist와 3단계의 Android 내장 자산 사이입니다. 이후 AAB 및 설치 기기 상태는 작업공간 증거만으로 확정할 수 없습니다.

Firebase 설정 변경만으로 해결되지 않는 이유

서버 측 변경만 한 경우

Firebase Authentication 설정, 허용 도메인, 보안 규칙 등 서버에 있는 설정은 앱이 다음 요청을 보낼 때 즉시 반영될 수 있습니다. 앱을 다시 배포할 필요가 없을 수 있습니다.

이번처럼 앱 코드도 바뀐 경우

메모리 전용 인증 지속성(inMemoryPersistence), 네이티브 로그인 자격 증명 처리(signInWithCredential), 진행도 로딩 흐름은 JavaScript 번들 안의 코드입니다. 기존 Android 앱은 과거 번들을 갖고 있으므로 새 AAB 배포가 필요합니다.

필수 조치 체크리스트

  1. 최신 소스에서 웹 빌드를 생성한다.
  2. Capacitor 동기화로 dist를 Android 내장 자산에 복사한다.
  3. Android versionCode를 27 이상으로 올린다.
  4. 릴리스 AAB를 생성하고, AAB 안의 내장 자산이 최신 dist와 연결되는지 확인한다.
  5. Google Play 테스트 트랙에 업로드하고, 테스트 기기에서 앱 업데이트를 완료한다.
  6. 업데이트된 기기에서 Google 로그인과 진행도 로딩을 실제로 다시 확인한다.

실행 명령 예시

cd Developer/r3f_prototype npm run build npx cap sync android
# Android versionCode를 27 이상으로 변경한 뒤 cd android ./gradlew bundleRelease

명령 실행 위치와 Gradle 래퍼 경로는 프로젝트의 실제 Android 구성에 맞춰 확인해야 합니다. AAB 생성 후 Play Console 업로드와 기기 업데이트는 별도 단계입니다.

점검 증거와 제한 사항

확인됨
웹 dist/index.html과 Android android/app/src/main/assets/public/index.html의 시각·크기·SHA-256·진입 번들이 모두 다릅니다.
확인됨
현재 웹 인증 번들에는 inMemoryPersistence 및 native signInWithCredential 표식이 있으며, Android의 과거 인증 번들에는 전자 표식이 없습니다.
미확인
작업공간에서 최종 릴리스 AAB를 찾지 못했습니다. 따라서 Play에 업로드된 AAB의 정확한 번들 상태는 이 점검만으로 판단할 수 없습니다.
미확인
ADB가 PATH에 없어 연결된 기기의 설치 버전과 실제 WebView 자산은 직접 조회하지 못했습니다.
