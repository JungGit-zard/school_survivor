### 1. 신규 Google 계정 진행도 생성 경로가 없다

- 상태: **해결됨(현재 작업트리, 미커밋)**

  - `users/{uid}`가 `null`일 때만 Realtime Database `runTransaction`으로 안전 기본 진행도를 생성한다.
  - 기존 원격 값이 있으면 트랜잭션 쓰기를 중단하고 기존 스냅샷을 그대로 hydrate한다.

  - 읽기·트랜잭션·최종 스냅샷 검증 실패는 `hydrated=false`와 저장 거부로 fail-closed 처리한다.
  - RTDB가 빈 객체 노드를 보존하지 않는 특성에 맞춰 빈 `weaponUnlocks`·`weaponPermanentUpgrades`·`passiveUpgrades` 맵을 필수 자식에서만 제외하고 각 자식값 검증 규칙은 유지했다.
- 검증:
  - `npm exec -- vitest run src/lib/firebaseProgress.test.js src/store/useAuthStore.cloudProgress.test.js src/lib/databaseRules.test.js` — 3 files/24 tests 통과

  - 실제 Firebase 및 Firebase Emulator는 실행하지 않았다.
- 근거:
  - `firebaseProgress.js`는 `users/{uid}`가 없으면 `missing-remote` 오류를 발생시킨다.
  - 빈 기본 진행도를 Firebase에 최초 생성하는 프로덕션 경로가 없다.
  - 기존 구현 TODO에도 “On first login, create new server progress with safe defaults”가 미완료로 남아 있다.
- 영향:
  - Firebase에 사용자 노드가 미리 만들어지지 않은 신규 Google 계정은 진행도 hydrate에 실패한다.
  - 닉네임, 골드, 무기, 스테이지 진행을 시작할 정본이 만들어지지 않는다.
- 필요 조치:

### 3. 적 엔티티 구조가 프로젝트 필수 안정성 규칙을 정면으로 위반한다

- 상태: **해결됨(현재 작업트리, 미커밋)**
- 해결 증거:
  - 일반 적은 `MAX_ENEMIES=200`의 SoA 고정 풀과 generation/free-list로 관리하며, 슬롯 재사용 뒤의 오래된 참조·피격 이벤트가 새 개체에 적용되지 않게 했다.
  - E01~E06 및 RZ는 개별 React 컴포넌트와 Rapier dynamic body를 만들지 않고 instancing으로 렌더하며, React/Rapier dynamic body는 보스·마틸다 등 특별 적 최대 3개에만 남겼다.
  - 적 생성·사망·피격과 투사체는 고정 이벤트/히트/투사체 큐로 처리하고, E01~E06/RZ 이동·접촉·특수 규칙은 풀 기반 시뮬레이션으로 실행한다.
  - 무기는 일반 적 풀을 직접 스캔하고 특별 적만 제한된 동적 목록으로 처리하여, 일반 적 `Map`/컴포넌트 의존을 제거했다.
- 검증:
  - 풀 기반 런타임 순수 soak 10,800 프레임(3분 상당)에서 큐 overflow/drop 0과 적·투사체 풀 상한을 확인했다.
  - 관련 15개 테스트 파일 192개 테스트 통과.
  - `npm run build` 통과.
  - 실제 브라우저 3분 soak는 감사 9번의 인증 자동화 진입 경로가 해결되기 전까지 **보류**한다. 따라서 이 기록은 브라우저 장시간 플레이 검증까지 완료되었다는 뜻이 아니다.

- 필수 정본: `Developer/agent_room/r3f_rapier_vampire_survivor_stability_rules.md`
- 기존 결함(감사 당시):
  - `Enemies.jsx`가 적 배열을 React state로 보관했다.
  - `enemies.map()`으로 적마다 `Enemy` 컴포넌트를 마운트했다.
  - 일반 적과 보스가 각각 `dynamic` Rapier `RigidBody`를 가졌다.
  - 웨이브 스폰·사망·드랍 때 배열 복사와 React `setState`를 수행했다.
  - `usePlayingFrame` 안에서 `setEnemies`, `setDoges`, `setGoldCoins` 등이 호출됐다.
- 감사 당시 위반 규칙:
  - RULE-0.1 프레임 콜백의 React state 갱신 금지
  - RULE-0.2 프레임 콜백의 배열·객체 생성 금지
  - RULE-0.3 엔티티 풀링
  - RULE-1.1 적 1마리당 컴포넌트 금지
  - RULE-1.2 SoA 고정 풀
  - RULE-4.1 다수 적 dynamic body 금지
- 해결 전 영향:
  - 후반 웨이브에서 적 수에 비례해 React 마운트·Rapier solver·GC 비용이 함께 증가했다.
  - 저사양 Android에서 프레임 저하, 입력 지연, 물리 떨림, 개체 소실 가능성이 구조적으로 남아 있었다.
  - 기존 구조에서는 최대 개체수 장시간 안정성을 코드만으로 보증할 수 없었다.

### 17. 프레임 안정성의 delta 상한이 필수 규칙보다 3배 느슨하다

- 영향:
  - 탭 복귀·프레임 정지 후 한 프레임에 최대 100ms를 처리한다.
  - 빠른 투사체, 근접 판정, 이동, 타이머가 큰 간격으로 건너뛰어 프레임별 결과가 달라질 수 있다.
  - `Game.jsx`는 같은 상한 delta만 `tickTime()`에 더한다. 실제 프레임 간격이 100ms를 넘으면 초과한 실제 시간이 통째로 사라져 저프레임 기기에서는 HUD 생존 시간, 보스·포탈·마틸다 등장, 마일스톤과 랭킹 시간이 실제 시간보다 느리게 간다.
  - 예를 들어 지속적으로 5FPS(프레임당 약 200ms)가 나오면 실제 4분을 플레이해도 `elapsedMs`에는 최대 약 2분만 누적될 수 있다.
- 현재 테스트는 store의 `tickTime()`을 직접 큰 값으로 호출할 뿐, `Game` 프레임 delta 상한과 실제 경과시간·랭킹 시간의 일치 여부를 검증하지 않는다.

- `saveTitleSettings()`는 메모리의 Firebase 진행도 스냅샷만 변경한다.
- `LobbySettingsModal`은 설정 변경 시 `saveTitleSettings()`만 호출하고 `requestCloudProgressSave()`를 호출하지 않는다.
- 같은 화면의 닉네임 저장은 명시적으로 `requestCloudProgressSave()`를 호출하므로 동작이 서로 다르다.
- 영향:
  - 진동·연출 줄이기를 바꾼 직후 로그아웃하거나 앱을 닫으면 변경이 Firebase에 기록되지 않을 수 있다.
  - 이후 플레이 기록이나 구매 등 다른 저장 이벤트가 우연히 발생해야 설정이 함께 저장된다.
  - “Firebase가 유일한 정본”이라는 정책을 UI가 안정적으로 충족하지 못한다.

### 29. “연출 줄이기” 설명과 실제 감소 대상이 다르다

- 설정 UI 설명: “강한 그림자와 빛 번짐을 낮춤”
- 실제 `data-reduced-effects` 소비처:
  - 로비 CSS 애니메이션
  - 보스 미리보기 모션
  - 데미지 숫자 표시
- 실제 게임의 조명, 그림자, 블룸·후처리에는 이 설정을 읽는 연결이 없다.
- 타이틀 3D는 설정과 관계없이 `reducedEffects={false}`로 고정되고, 타이틀 진입 시 전역 설정도 강제로 해제된다.
- 영향:
  - 광과민성·저사양 대응을 기대하고 켜도 설명된 핵심 효과가 줄어들지 않는다.
  - 대신 전투 정보인 데미지 숫자가 사라져 설명하지 않은 가독성 손실이 생긴다.

### 30. 게임 전체 음량·음소거 설정이 없다

- 타이틀 BGM은 0.5 고정 음량으로 자동 재생을 반복 시도한다.
- 게임 효과음은 개별 코드와 그래픽 스튜디오 튜닝값으로 재생되지만 플레이어용 마스터 음량이 없다.
- 로비 설정에는 진동과 연출 줄이기만 있고 BGM·효과음 음량 또는 음소거가 없다.
- 영향:
  - 출퇴근·학교 같은 무음 환경에서 게임을 켜기 어렵다.
  - 접근성 및 사용자 환경 제어가 부족하다.

### 31. 스테이지 4 로비 보스 쇼타임이 스테이지 1 연출로 잘못 폴백된다

- `BOSS_SHOWTIME`에는 B01, B02, B03만 있고 B04가 없다.

  - 효과음: B01의 `bossRoar`, `bossSpawn`
- 실제 B04는 원거리 포격 후 격노 돌진하는 주방장 보스다.
- 영향:
  - 최종 스테이지 입장 연출이 다른 보스의 정체성을 광고한다.
  - B04 전용 모델·행동이 구현돼 있는데 로비 콘텐츠만 미완성이다.

### 32. 조사로 받은 10골드 보상이 즉시 Firebase에 저장되지 않는다

- 조사 성공 시 10% 확률 보상은 업그레이드 또는 10골드다.
- 골드 보상 수령 시 `saveGoldTotal()`로 메모리 진행도와 현재 런 골드를 갱신하지만 `requestCloudProgressSave()`를 호출하지 않는다.
- 일반 코인 획득과 생존 마일스톤은 같은 골드 갱신 뒤 클라우드 저장을 요청한다.
- 영향:
  - 조사 보상을 받은 직후 앱 종료·로그아웃·비정상 종료가 발생하면 해당 10골드가 사라질 수 있다.
  - “중요한 조사 보상”이 일반 필드 코인보다 저장 신뢰도가 낮다.

### 33. Firebase 저장이 한 번 실패하면 이후 저장 큐 전체가 계속 실패한다

- 저장 큐는 `writeQueue = writeQueue.then(async () => client.save(...))` 형태다.
- 한 번의 `client.save()`가 네트워크·권한 오류로 reject되면 `writeQueue`가 거부 상태가 된다.
- 다음 요청도 거부된 Promise의 `.then()`에 연결되므로 저장 본문이 실행되지 않고 즉시 reject된다.
- 정상 상태로 되돌리는 `.catch()` 또는 큐 복구 분기가 없다.
- 대부분 호출부는 `requestCloudProgressSave()`를 `await`하거나 실패를 처리하지 않는다.
- 영향:
  - 일시적인 통신 장애 한 번이 앱을 다시 열 때까지 모든 진행도 저장을 중단시킬 수 있다.
  - 골드, 구매, 기록, 해금이 화면에는 반영되지만 Firebase에는 남지 않는 조용한 데이터 손실이 발생한다.
  - 저장 실패 팝업·재시도·미저장 상태 표시가 없어 사용자가 이를 알 수 없다.

## 추가 P0 — 서비스 무결성

### 34. 랭킹 서버가 실제 플레이 결과를 검증하지 않는다

- Callable Function은 로그인 여부와 다음 형식만 검사한다.
  - stageId가 stage1~3인지
  - score가 1~100,000 정수인지
  - timeMs가 0~3,600,000 정수인지
  - cleared가 boolean인지

- 따라서 인증 사용자가 직접 `score=100000`, `timeMs=0`, `cleared=true`를 제출해도 유효한 런으로 누적된다.
- 같은 사용자가 매번 새 `runId`를 만들면 일일·주간 점수를 제한 없이 반복 누적할 수 있다.
- 영향:
  - 공개 랭킹은 실제 실력 순위로 신뢰할 수 없다.
  - 정상 사용자의 기록이 임의 제출 한 번으로 밀려날 수 있다.

### 35. 사용자 진행도 Rules가 재화·강화의 합법적인 획득 과정을 검증하지 않는다

- 사용자는 자신의 `users/{uid}` 전체 진행도를 직접 쓸 수 있다.
- Rules는 범위만 검사하므로 다음 값도 클라이언트가 직접 만들 수 있다.
  - 골드 최대 10억
  - 임의 record key 최대 10억
  - 임의 weaponId 해금
  - 모든 영구 무기 강화 Lv.10
  - 패시브 Lv.100
- 구매 전후 골드 차감, 실제 클리어 여부, 허용 ID 목록, 패시브별 최대 레벨은 서버에서 검증하지 않는다.
- 영향:
  - 싱글 플레이 성장과 해금이 쉽게 조작된다.
  - 조작된 영구 능력으로 공개 랭킹에 참가할 수 있어 랭킹 검증 부재와 결합된다.

### 36. 랭킹 시즌의 draft/live/closed 상태가 실제 동작에 반영되지 않는다

- 관리자 설정에는 `status: draft | live | closed`가 있다.
- `getActiveSeason()`은 시작일·종료일만 확인하며 status를 전혀 읽지 않는다.
- 따라서 draft 또는 closed 시즌도 날짜 범위가 맞으면 제출·조회가 활성 상태다.
- 영향:
  - 운영자가 시즌을 닫았다고 표시해도 점수가 계속 들어올 수 있다.
  - 보상 정산 기간의 순위가 뒤늦게 바뀔 수 있다.

### 37. 클라이언트와 서버의 랭킹 시즌 정본이 서로 다르다

- 클라이언트는 메모리 전용 관리자 설정의 `seasonId`를 사용해 랭킹을 읽는다.

- 두 값의 공유 Firebase 정본이나 동기화 검증이 없다.
- 영향:
  - 서버 환경변수가 바뀌면 제출은 새 시즌으로 들어가지만 게임 화면은 이전 시즌을 읽을 수 있다.
  - 사용자는 제출 성공 응답을 받아도 자신의 점수를 찾지 못한다.

### 38. 프로덕션 타이틀에 영구 해금 치트가 포함돼 있다

- 모든 빌드에서 키 입력 `↑ ↓ ↑ ↓ A S D`를 감지한다.
- 성공하면 모든 무기·모든 스테이지 해금과 패시브 초기화 메뉴가 노출된다.

- 영향:
  - 일반 사용자가 정규 진행을 건너뛰고 강화된 상태로 랭킹에 참가할 수 있다.

- 테스트 전에 해당 Firebase 경로의 전체 값·revision·해시 스냅샷을 만들지 않았고, 종료 후 동일성 비교도 수행하지 않았다.
- 이번 실행은 Rules가 쓰기를 거부해 데이터 변경이 확인되지 않았지만, 권한이나 Rules가 달라지면 단위 테스트가 실제 사용자 정본을 오염시킬 수 있다.
- 영향:
  - 프로젝트의 “테스트 전후 Firebase 상태 절대 동일성” 법칙을 구조적으로 보장하지 못한다.
  - 테스트 성공·실패가 네트워크와 배포된 Rules 상태에 따라 달라진다.
  - 모든 단위 테스트는 네트워크가 없는 명시적 fake Firebase client를 기본 설치하고, 실제 Firebase 통합 테스트는 별도 격리 프로젝트·완전 스냅샷·복원 검증이 없으면 실행을 차단해야 한다.

### 57. 필수 브라우저 인스턴스 상한 가드가 검사 실패를 성공으로 처리한다

- 프로젝트 정책은 새 수동 Chrome·CDP·Playwright 실행 전에 `npm run browser:reserve`로 총 3개 상한을 확인하도록 요구한다.
- 실제 실행에서 `guard-game-browser-limit.ps1`의 `netstat` 호출이 `CommandNotFoundException`으로 실패했다.
- 스크립트는 이 오류를 종료 실패로 전파하지 않고 `GAME_BROWSER_INSTANCES=0 LIMIT=3 MODE=reserve`를 출력하며 성공 코드로 끝났다.
- 영향:
  - 실행 중인 브라우저가 있어도 항상 0개로 오판할 수 있어 필수 동시 실행 상한이 작동하지 않는다.
  - 중복 GPU/WebGL 브라우저 때문에 성능 측정이 왜곡되거나 시스템 자원이 고갈될 수 있다.
  - 프로세스 조사 실패는 fail-closed로 명령을 중단하고, 현재 WSL/Windows 환경에서 실제 사용 가능한 조회 방식으로 교체해야 한다.

### 60. 치비코의 “모든 무기 능력 10% 상승”이 일부 수치에만 적용된다

- 치비코 획득 시 `applyChibikoAllWeaponBoost()`가 활성 무기를 순회하는 연결 자체는 구현돼 있다.
- 그러나 강화 목록은 일부 연속형 수치만 포함하며 다음 핵심 능력을 제외한다.
  - 연필 `projectileCount`, `pierce`
  - 텀블러·오리요강 `count`
  - 벨 `directions`
  - 전기 `chainCount`
  - 오니기리 `bounces`, `bounceRange`
  - 스타링크 `strikeCount`, `strikeCenter`
  - 텀블러·오리요강 `hitsPerSecond`
  - 랜턴 `lightBaseWidth`
- 구현 주석도 정수 능력을 의도적으로 제외한다고 명시해, 사용자 요구인 “주인공이 가진 모든 무기 능력의 10% 상승”과 직접 충돌한다.

- 영향:
  - 같은 “모든 능력” 문구를 보고도 무기별 실제 강화 폭이 크게 다르다.
  - 투사체·체인·바운스 기반 무기는 핵심 정체성 수치가 전혀 오르지 않아 치비코 조합 가치가 불균등하다.
  - 정수 능력을 10%로 표현하는 반올림·누적 규칙을 기획으로 확정하거나, UI 문구를 실제 대상 수치에 맞게 제한해야 한다.

### 61. 탈출구가 도달 불가능한 위치나 현재 소품 안에 생성될 수 있다

- `EscapePortal.pickPortalPosition()`은 스테이지 외곽에서 3만큼 안쪽을 무작위 선택하지만 실제 플레이어 이동 경계는 북쪽에서 4만큼 안쪽이다.

- 40회 후보가 모두 실패하면 플레이어·장애물·도달 가능성을 확인하지 않고 무조건 `[0, 0.05, 0]`에 생성한다.
- 탈출구 위치·Firebase 소품 오버라이드·fallback 도달 가능성을 검증하는 테스트가 없다.
- 영향:
  - 생존 조건을 달성해도 탈출구에 들어갈 수 없어 런을 클리어하지 못할 수 있다.
  - Studio Apply 이후 화면에는 옮겨진 소품이 보이지만 탈출구 배치 판정은 과거 소품 위치를 기준으로 해 정본 패리티가 깨진다.
  - 스테이지별 플레이어 이동 경계와 현재 collider를 함께 사용하는 도달 가능한 지점 계산이 필요하다.

### 62. 일반·원거리·편대 적 생성이 장애물 충돌 영역을 전혀 검사하지 않는다

- `Enemies.jsx`의 일반·원거리 링 스폰은 맵 경계, 플레이어와의 거리, 같은 배치 묶음의 적 간격만 검사한다.

- 도지는 모든 스테이지에서 고정 좌표 `[0, 0, 0]`, 마틸다는 일반 랜덤 스폰을 사용하며 두 특수 이벤트도 현재 소품 collider를 검사하지 않는다.

- Firebase Studio에서 소품을 이동·추가해도 스폰 안전 영역은 갱신되지 않는다.
- 영향:
  - 적이 고정 collider 내부에서 튕겨 나오거나 끼고, 원거리 E04가 보이지 않는 장애물 안에서 공격할 수 있다.
  - 편대 형태가 장애물에 의해 즉시 깨져 기획된 포위·협공·건틀릿 패턴이 성립하지 않을 수 있다.
  - 스폰 테스트는 맵 경계와 적 간격만 검증하며 collider 비중첩은 검증하지 않는다.

### 63. 탈출구가 최신 로비 기획을 무시하고 다음 스테이지를 즉시 시작한다

### 64. 최신 로비 허브의 핵심 정보와 능력치 진입점이 연결되지 않았다

- 영향:

  - 로비가 플레이→성장→다음 런을 준비하는 허브 역할을 완성하지 못한다.
  - 랭킹 상세 화면을 매번 열기 전에는 시즌 경쟁 상황을 스테이지 선택 화면에서 알 수 없다.

### 65. E04 탄환이 불투명한 복도 소품과 물리 벽을 그대로 관통한다

- `Enemy.jsx`의 `EnemyProjectile`은 sensor body이며 교차 이벤트에서 `_playerHit`가 달린 플레이어만 처리한다.
- 게시판·사물함·책상·카트 등 fixed collider 또는 맵 경계와 교차해도 탄환을 소멸시키거나 막는 분기가 없다.
- 탄환은 최대 3.2초 동안 유지되므로 불투명한 사물함이나 벽 뒤에서도 계속 날아와 플레이어를 맞힐 수 있다.
- 스테이지 2 기획은 “맞기 전에 위험을 알아볼 수 있고, 회피할 공간이 보이며, 실패 이유를 이해할 수 있어야 한다”는 공정성을 난이도보다 우선한다.
- 현재는 장애물 뒤에서 탄환의 시각 정보가 가려져도 판정은 통과하므로 이 공정성 원칙과 충돌한다.
- 탄환과 스테이지 collider의 차폐 계약 및 회귀 테스트가 없다.
- 영향:
  - 사물함·게시판 조사를 위해 가까이 갔을 때 보이지 않는 탄환에 맞을 수 있다.
  - 플레이어가 소품을 엄폐물로 읽었는데 실제로는 아무 보호도 제공하지 않아 공간 규칙을 학습하기 어렵다.
  - “소품은 탄환을 막지 않는 장식”이 의도라면 시각적으로 탄환을 가리지 않게 만들고 명시해야 하며, 아니라면 현재 Firebase 소품 collider와 탄환 충돌을 연결해야 한다.

### 66. 최종 스테이지 클리어에 전용 결말·완주 피드백이 없다

- 스테이지 4는 `getNextStageId('stage4') === null`이라 다음 스테이지로 넘어가지는 않지만, HUD에는 다른 스테이지와 같은 일반 `STAGE CLEAR!` 결과창만 표시된다.
- 스테이지 4 제목·보스·급식실 탈출을 마무리하는 전용 문구, 엔딩 장면, 크레딧, 최종 완주 배지 또는 로비의 완주 상태 변화가 없다.
- 결과창에서 제공되는 행동도 랭킹·타이틀·코인상점·다시 시작으로 일반 스테이지와 동일하다.
- 소스와 현재 기획 문서 검색에서도 최종 스테이지 결말 계약이나 엔딩 콘텐츠는 발견되지 않았다.
- 영향:
  - 네 스테이지 진행의 마지막 목표를 달성해도 일반 중간 스테이지 종료처럼 보여 완주 감각이 없다.
  - 결말이 의도적으로 미기획된 것인지 구현 누락인지 판단할 정본이 없다.
  - 출시 전 최소한 최종 완주 메시지·로비 완주 표시·후속 목표를 기획으로 확정하고 테스트해야 한다.

### 67. Graphics Studio Apply 후 조사 판정만 과거 위치에 남는다

- `StageObjectLayer`와 `StageObjectColliderLayer`는 `useStagePropPlacementsVersion()`을 구독해 Firebase Studio 프랍 Apply 때 시각 모델과 collider를 다시 계산한다.
- 반면 `StudentDialogueTrigger`는 조사 대상 목록을 `useMemo(..., [currentStageId])`로만 계산하고 프랍 배치 version을 구독하지 않는다.
- 따라서 런 도중 사물함·불레틴보드·학생 위치를 Studio에서 Apply하면 모델과 충돌체는 새 위치로 이동하지만 조사 판정은 이전 좌표를 계속 사용한다.
- 새 위치에서는 아무리 가까이 가도 조사가 발동하지 않고, 화면에 아무것도 없는 옛 위치에서 조사창이 열릴 수 있다.
- 기존 `studentProximity` 테스트는 정적 배치와 순수 거리 함수만 검사해 Apply 이후 재계산을 검증하지 않는다.
- 영향:
  - “Studio Apply가 게임에 즉시 적용된다”는 Firebase 정본 계약이 조사 시스템에서 깨진다.
  - 조사 대상과 실제 판정 위치가 분리되어 콘텐츠를 정상적으로 찾을 수 없다.
  - 조사 트리거도 프랍 version을 구독하고 현재 Firebase 배치로 대상 목록을 다시 계산하는 통합 테스트가 필요하다.

### 68. 스테이지 2 편대 공격은 예고만 나오고 실제로 생성되지 않는다

- `STAGE2_BURST_EVENTS`에는 30초 swarm, 60초 ring, 132초 pincer, 176초 swarm 편대가 정의돼 있다.
- `STAGE2_SPAWN_TELEGRAPHS`와 HUD는 이 시각에 맞춰 편대 경고를 표시한다.
- 그러나 `getRuntimeBurstEventsForStage()`는 스테이지 3·4만 전체 이벤트를 반환하고, 스테이지 1·2에서는 `isBossType()`인 이벤트만 남긴다.
- 결과적으로 스테이지 2에서는 B02 보스만 버스트로 생성되고 네 개 편대 이벤트는 모두 런타임에서 제거된다.
- `Enemies.jsx` 주석도 “stage1/stage2는 보스 등장만”이라고 명시하지만, 같은 데이터 파일의 스테이지 2 편대 주석은 실제 발화를 전제로 해 서로 모순된다.
- 영향:
  - HUD가 곧 일어날 공격을 예고하지만 아무 일도 일어나지 않아 경고의 신뢰가 무너진다.
  - 균일한 압력을 깨는 스파이크→이완 리듬과 포위·협공이라는 스테이지 2 콘텐츠가 통째로 비활성화돼 있다.
  - 테스트가 편대 데이터 존재와 HUD 문구만 확인하고 실제 런타임 이벤트 반환을 끝까지 검증하지 못한다.

### 69. 스테이지 3·4 보스 경고가 실제 등장 전에 끊긴다

- HUD는 `bossWarningSec - 3`부터 `bossWarningSec` 직전까지만 3초 카운트다운을 표시한다.
- 스테이지 1·2는 `bossWarningSec=120`이고 보스도 120초에 생성돼 카운트다운 직후 등장한다.
- 스테이지 3은 경고 설정이 129초지만 B03은 135초, 스테이지 4는 경고 설정이 134초지만 B04는 140초에 생성된다.
- 따라서 스테이지 3·4는 “3, 2, 1” 경고가 끝난 뒤 아무 일도 없는 6초 공백을 거쳐 보스가 갑자기 등장한다.
- 설정 주석은 `bossWarningSec`를 “등장 6초 전”이라고 설명하지만 HUD는 이를 경고 시작이 아니라 카운트다운 종료 시각으로 해석한다.
- 현재 HUD 테스트는 경고가 132초에 보이는지만 확인하고, 경고 종료와 실제 보스 생성의 연속성을 검증하지 않는다.
- 영향:
  - 카운트다운의 1이 보스 등장과 연결되지 않아 사용자에게 잘못된 시간 정보를 준다.
  - 보스 대비 위치 선정과 회피 준비 타이밍이 스테이지마다 다르게 작동한다.
  - 보스 실제 생성 시각에서 경고 구간을 파생하거나 설정 의미를 하나로 통일해야 한다.

### 70. `matildaWarningSec`는 네 스테이지 모두 실제 HUD에 적용되지 않는다

- `stageConfig.js`는 스테이지별 `matildaWarningSec`를 170·170·210·205초로 정의하고 테스트도 해당 값을 검증한다.
- 그러나 HUD는 이 값을 전혀 읽지 않고 `matildaSec - MATILDA_COUNTDOWN_SECONDS(5)`를 하드코딩해 경고 시작 시각을 계산한다.
- 실제 경고 시작은 스테이지 1·2에서 175초, 스테이지 3에서 215초, 스테이지 4에서 210초다.
- 따라서 설정에 적힌 의도보다 모두 5초 늦게 경고하며, 관리자나 기획자가 `matildaWarningSec`를 바꿔도 런타임에는 아무 영향이 없다.
- 영향:
  - 경고 시각의 단일 정본처럼 보이는 설정과 실제 동작이 분리돼 밸런스 조정이 실패한다.
  - 테스트는 값의 존재만 확인해 실제 HUD 소비 누락을 잡지 못한다.
  - `matildaWarningSec`를 실제로 소비하거나 제거하고, 등장 시각과 경고 길이 중 무엇이 정본인지 명확히 해야 한다.

### 71. 관리자 “생존 시간” 변경이 실제 스테이지 길이를 바꾸지 않는다

- 관리자 페이지는 스테이지 1·2 `stageDurationSec`를 120~420초 범위로 편집하며 “생존 시간”이라고 표시한다.
- `getStageConfig()`는 이 값을 `durationSec`에 반영하지만 실제 포탈 생성은 별도 고정값 `escapePortalSec`, 보스·마틸다·웨이브도 각 고정 타임라인을 사용한다.
- `Game.jsx`에는 `durationSec` 도달로 클리어하거나 포탈을 여는 로직이 없다.
- 예를 들어 관리자가 스테이지 2 생존 시간을 120초로 바꿔도 포탈은 계속 240초에 열리고, B02는 120초, 마틸다는 180초, 웨이브는 240초 표를 그대로 따른다.
- 관리자 미리보기는 변경한 duration을 클리어 점수 계산에 사용해 실제 런과 다른 점수를 보여준다.
- 영향:
  - 운영자가 시간 밸런스를 바꿨다고 생각해도 플레이 규칙은 바뀌지 않는다.
  - 설정값에 따라 보스·포탈·마틸다·마일스톤·랭킹 점수의 시간축이 서로 분리된다.
  - 생존 시간 입력을 제거하거나 모든 시간 이벤트를 동일한 duration 정본에서 비례 파생해야 한다.

### 72. 관리자 “골드 보상 배율”은 전체 골드가 아니라 생존 마일스톤에만 적용된다

- 관리자 페이지는 제한 설명 없이 `골드 보상 배율` 하나를 제공한다.
- 실제 `goldMultiplier` 소비처는 `stageConfig.js`의 `survivalMilestones`뿐이다.
- 시간제 일반 골드 드랍, 적·엘리트·보스 드랍, 도지 보물, 조사 보너스 10골드, 기타 `gainGold()` 호출에는 배율이 적용되지 않는다.
- 따라서 배율을 0으로 설정해도 필드에서는 계속 골드를 획득할 수 있고, 3배로 설정해도 대부분의 드랍은 1배다.
- 영향:
  - 관리자 UI의 명칭과 실제 경제 조절 범위가 다르다.
  - 플레이 방식에 따라 동일한 운영 설정의 효과가 크게 달라져 경제 밸런스 예측이 불가능하다.
  - “생존 마일스톤 배율”로 정확히 표시하거나 모든 골드 생성 경로의 단일 정책으로 통합해야 한다.

### 73. 스테이지 2 결과창에 사망 원인·개선 힌트가 없다

- 스테이지 2 정본 기획은 결과창에 사망 원인에 따른 이동 속도·최대 체력·광역 무기 추천을 표시하도록 명시한다.
- 현재 게임오버 결과창은 생존 시간, 획득·누적 골드, 새 무기 해금, 다음 무기 윤곽, 네 개 이동 버튼만 보여준다.
- `damagePlayer()`는 피해량과 남은 HP만 기록하며 마지막 피해의 출처가 접촉, E04 탄환, 돌진, 보스 필살기 중 무엇인지 상태에 남기지 않는다.
- 따라서 UI 누락뿐 아니라 사망 원인 분류에 필요한 데이터 계약 자체가 없다.
- 영향:
  - 탄환 회피와 안전 레인을 학습해야 하는 스테이지에서 사용자가 왜 죽었는지 알 수 없다.
  - 동일한 실패를 반복해도 다음 판의 성장·무기 선택에 연결되는 안내가 없다.
  - 피해 호출에 원인 ID를 전달하고 마지막 유효 피해 원인을 결과 화면까지 검증하는 테스트가 필요하다.

### 74. 즉시 중도 종료 반복만으로 누적 플레이 무기를 해금할 수 있다

- 일시정지 확인창의 “로비로 돌아가기”는 `quitPausedRun()`을 호출하고 `_onRunEnd('quit')`로 종료 기록을 남긴다.
- `_onRunEnd()`는 생존 시간이나 최소 활동 조건과 무관하게 모든 종료에서 `totalRuns`를 1 증가시킨다.
- 보조배터리 미사일은 `totalRuns=5`, 상어미사일은 8, 스타링크는 10, 학생용 랜턴은 5회 조건을 OR 해금 조건으로 사용한다.
- 따라서 스테이지 시작 직후 일시정지→로비 복귀를 10회 반복하면 전투·생존·처치 없이 이 무기들을 해금할 수 있다.
- 같은 종료는 Firebase 진행 저장과 미클리어 랭킹 제출 경로도 호출한다.
- 영향:
  - 누적 플레이가 실제 도전 횟수가 아니라 메뉴 반복 횟수로 변해 메타 진행의 의미가 사라진다.
  - 신규 사용자가 의도한 성장 곡선을 즉시 건너뛸 수 있다.
  - 중도 종료 기록 정책과 무기 해금용 유효 런의 최소 생존·활동 조건을 분리해야 한다.

### 75. 레벨업 카드 추첨에 기획된 종류별 가중치가 없다

- 무기 성장 기획은 보유 무기 강화 50~55%, 신규 무기 획득 25~30%, 패시브 20%의 추천 비율을 명시한다.
- 현재 `pickThree()`는 사용 가능한 카드를 무기별 한 장으로 줄인 뒤 `sort(() => Math.random() - 0.5)`로 균등 셔플하고 앞의 세 장을 자른다.
- 보유 무기 강화·신규 획득·패시브라는 카드 종류를 분류하거나 가중치를 적용하는 로직이 없다.
- 예를 들어 레벨 2의 기본 계정은 연필 강화군 1장, 30cm 자·커터칼·텀블러 획득 3장, 패시브 2장으로 압축돼 후보 비중이 강화 약 17%, 신규 획득 50%, 패시브 33%가 된다.
- 무기가 많이 해금될수록 신규 획득 후보 수에 따라 확률이 다시 바뀌므로 계정 진행도별 성장 곡선도 일정하지 않다.
- 영향:
  - 초반에 보유 무기를 키우는 대신 카드 풀이 지나치게 퍼져 화력 성장 체감이 약해질 수 있다.
  - 카드 비율을 전제로 한 적 HP·웨이브 밸런스가 실제 추첨과 맞지 않는다.
  - 종류별 가중 추첨과 계정 상태별 분포 통계 테스트가 필요하다.

### 76. 플라스크 피해·범위 카드가 실제 추가 효과를 숨긴다

- `flaskDamage`, `flaskRadius`, `flaskCrit`는 모두 `bonus: { zoneDurationMs: +1000 }`을 가져 웅덩이 지속시간을 1초 늘린다.
- 치명타 카드 설명에는 “웅덩이 지속 +1초”가 표시되지만 피해 카드는 “폭발 피해 증가”, 범위 카드는 “폭발 반경 증가”만 표시한다.
- 같은 실효 효과를 가진 세 카드 중 두 장만 플레이어에게 정보를 감춘다.
- 영향:
  - 사용자는 지속시간 증가를 모르고 선택해 빌드 판단과 카드 비교를 정확히 할 수 없다.
  - 표시 문구를 기준으로 한 체감 피해와 실제 성능 상승 폭이 다르다.
  - 카드 설명을 효과 객체에서 생성하거나 세 카드 모두 동일한 부가 효과를 명시해야 한다.

### 77. 골드 픽업은 장애물·경계 도달 가능성을 검증하지 않는다

- 교과서는 `computeTextbookLanding()`으로 맵 경계와 현재 소품 collider를 피해 도달 가능한 착지점을 계산한다.
- 반면 시간제 골드는 가까운 적 위치를 그대로 사용하거나 플레이어 주변 링을 경계에 단순 clamp할 뿐 소품 collider를 확인하지 않는다.
- 엘리트·보스 골드는 사망 좌표에 여러 개를 겹쳐 생성하므로, 장애물 안에 생성된 적 문제와 결합하면 골드도 같은 장애물 내부에 남는다.
- 도지 보물상자 코인은 처치 위치에서 최대 1.4유닛을 추가 산포하지만 맵 경계와 장애물을 전혀 검사하지 않는다. 도지를 경계 근처에서 처치하면 벽 밖으로 나갈 수 있다.
- 골드의 포물선 비행도 Rapier 충돌이나 최종 경계 clamp 없이 좌표만 갱신한다.
- 자석 미강화 상태의 흡입 반경은 0이고 직접 수집 반경은 0.38뿐이라 벽·소품 내부나 경계 밖 골드는 회수할 수 없다.
- 영향:
  - 보스·도지 같은 중요한 보상이 화면에 보이면서도 획득 불가능할 수 있다.
  - 골드 경제 실측이 실제 생성량과 실제 회수 가능량으로 분리된다.
  - 모든 골드 경로도 교과서와 같은 현재 Firebase collider·이동 경계 기반 착지 검증을 사용해야 한다.

### 78. B01·B02·B03 보스 드랍 보상은 생성되지만 수집할 수 없다

- 보스 HP가 0이 되면 `Enemy.jsx`는 `recordBossKill()` 다음 `clearStageWithBossBonus()`를 먼저 호출한다.
- 이 함수는 즉시 phase를 `cleared`로 바꾸고 `_onRunEnd('cleared')`로 결과 골드·기록·랭킹을 확정한다.
- 그 뒤에야 `onDeath()`가 호출되고 `ELITE_BONUS`의 교과서 3개(XP 40)와 골드 5개가 생성된다.
- `GoldCoin`과 `XpTextbook`은 phase가 `playing`이 아니면 매 프레임 즉시 반환하므로, 결과창 뒤에서 정지한 채 수집될 수 없다.
- 결과창을 닫아 현재 런으로 복귀하는 경로도 없고 재시작하면 Enemies 컴포넌트가 초기화되므로 보상은 소멸한다.
- B04는 애초에 `ELITE_BONUS`에서 누락돼 있고, B01·B02·B03은 목록에는 있지만 위 호출 순서 때문에 실효 보상이 0이다.
- 기존 테스트는 상수와 드랍 호출문 존재만 확인하며 보스 사망→phase 전환→실제 수집까지 검증하지 않는다.
- 영향:
  - 보스 보상으로 광고·기획된 XP 120과 골드 5를 플레이어가 받을 수 없다.
  - 강한 빌드로 보스를 처치할수록 생존 마일스톤뿐 아니라 보스 드랍까지 잃는다.
  - 보상을 즉시 계정·런 상태에 지급하거나, 수집 가능한 보상 단계 이후에 클리어를 확정해야 한다.

### 79. Rapier 물리가 렌더 프레임률에 종속돼 기기별 판정이 달라질 수 있다

- 게임의 최상위 `Physics`는 `timeStep="vary"`를 사용한다.
- 이 설정은 렌더 프레임마다 달라지는 delta를 그대로 물리 계산에 사용하므로, 같은 입력과 같은 전투라도 30Hz·60Hz·120Hz 또는 순간 프레임 저하 상황에서 물리 결과가 달라질 수 있다.
- 프로젝트 필수 안정성 체크리스트 `CHECK-4.6`은 프레임률에 따라 물리 결과가 달라지는 문제를 막기 위해 고정 timestep을 유지하도록 명시한다.
- 플레이어와 적의 접촉, 넉백, 센서 교차, 빠른 이동체의 관통 여부가 물리 스텝 크기에 영향을 받기 때문에 단순 시각 차이가 아니라 피격 결과와 난이도 차이로 이어질 수 있다.
- 현재 자동 테스트는 `Physics`의 timestep 계약이나 서로 다른 프레임률에서 동일한 충돌 결과가 나오는지 검증하지 않는다.
- 영향:
  - 데스크톱에서는 피한 공격이 저사양 Android에서 맞거나, 반대로 충돌이 누락될 수 있다.
  - 적이 몰리는 후반부 프레임 저하가 곧 물리 판정 변화와 난이도 급변으로 연결될 수 있다.
  - 고정 timestep으로 통일하고 물리 동기화 로직을 물리 스텝 기준으로 검증해야 한다.

### 80. `totalPickups`와 `weaponMasterCount` 영구 진행 기록은 실제 게임에서 영원히 0이다

- Firebase 플레이어 진행 스키마와 `playerRecords.RECORD_KEYS`에는 `totalPickups`와 `weaponMasterCount`가 정식 기록으로 등록돼 있다.
- 무기 확장 기획은 드랍 아이템 획득 시 `totalPickups`, 새 무기가 런 중 Lv.5에 처음 도달할 때 `weaponMasterCount`를 갱신하도록 명시한다.
- 그러나 `GoldCoin`, `XpOrb`, `XpTextbook`의 실제 수집 성공 경로는 골드·XP만 지급하며 두 기록 중 어느 것도 증가시키지 않는다.
- 레벨업 카드 적용 경로도 무기 레벨을 최대 5까지 올리지만, 처음 Lv.5에 도달한 무기 종류를 식별하거나 `weaponMasterCount`를 증가시키지 않는다.
- 전체 운영 코드에서 두 키는 스키마 선언과 읽기 목록 외에는 참조되지 않는다. `playtestLogger`의 `totalPickups`는 판별 로그용 모듈 내부 변수라 Firebase 플레이어 기록과 연결되지 않는다.
- 영향:
  - 수집형·숙련자용 무기 해금 조건을 이 기록에 연결하는 순간 정상 플레이로는 절대 해금되지 않는다.
  - 계정 데이터에는 기능이 있는 것처럼 키가 유지되지만 플레이 이력이 반영되지 않아 분석·운영 지표도 거짓 0이 된다.
  - 실제 수집 완료와 무기 최초 Lv.5 전환을 중복 없이 Firebase 기록에 반영하고, 재수집·동일 무기 재숙련·중도 종료를 포함한 통합 테스트가 필요하다.

### 81. 탈출구를 무시하면 240초 이후에도 무제한 생존 점수를 올릴 수 있다

- `durationSec=240`은 화면 설명과 일부 판정에서만 사용되고, `Game.jsx`에는 해당 시간에 런을 종료하거나 elapsed를 고정하는 로직이 없다.
- 240초에 실행되는 것은 `escapePortalActive=true`뿐이며 플레이어가 포탈에 들어가지 않으면 phase는 계속 `playing`이고 `elapsedMs`도 계속 증가한다.
- 런 종료 시 랭킹 점수는 상한 없이 `floor(elapsedMs / 1000)`를 그대로 더하며, 개인 최고 생존 기록과 누적 생존 시간에도 같은 값이 저장된다.
- 서버도 스테이지별 240초 계약을 검증하지 않고 `MAX_RUN_TIME_MS=3_600_000`, 즉 최대 1시간을 정상 런으로 허용한다.
- 따라서 포탈을 무시하고 30분 생존한 런은 정상 4분 클리어보다 생존 점수만 약 7.5배 높고, 59분대 런도 서버 형식 검사를 통과한다.
- 1시간을 넘기면 클라이언트의 `.catch(() => {})` 때문에 제출 실패가 사용자에게 표시되지 않는다.
- 영향:
  - 랭킹의 최적 전략이 보스 처치·탈출이 아니라 포탈을 피하며 최대한 오래 버티는 것으로 바뀐다.
  - 정상 240초 콘텐츠를 플레이한 사용자는 장기 카이팅 기록을 점수로 이길 수 없다.
  - 런타임 종료 계약과 서버의 스테이지별 시간·점수 재계산을 240초 정본에 맞추고 초과 제출을 명시적으로 거부해야 한다.

### 82. 도지 보물상자는 열리는 순간 삭제돼 550ms 오픈 연출이 보이지 않는다

- `TreasureChest`는 1.5초 후 `burst=true`로 바꾸고 뚜껑 열림·금빛 플래시·팝 소멸을 `CHEST_BURST_MS=550` 동안 재생하도록 구현돼 있다.
- 그러나 같은 프레임에 `onOpen(id, position)`을 호출하고, 부모 `Enemies.onChestOpen()`은 즉시 해당 ID를 `chests` 배열에서 제거한다.
- 부모 재렌더에서 `TreasureChest`가 바로 언마운트되므로 컴포넌트 내부의 `burst` 상태와 이후 프레임 애니메이션은 렌더될 기회가 없다.
- 코인 12개는 부모에서 즉시 생성되지만, 코인이 상자에서 터져 나오는 원인 연출인 뚜껑·플래시·상자 소멸은 사라진다.
- 기존 테스트는 `CHEST_OPEN_DELAY_MS=1500`, 소스 문자열, 콜백 배선만 확인하고 실제 1.5초→오픈→550ms 유지→제거 수명주기를 렌더하지 않는다.
- 영향:
  - 도지 처치 보상이 닫힌 상자가 갑자기 사라지고 코인만 생기는 것처럼 보인다.
  - 공들여 구현한 오픈 피드백과 효과음의 시각적 동기가 분리된다.
  - 코인 생성과 상자 제거를 분리해 오픈 순간에는 보상만 지급하고, 상자 제거는 내부 버스트 완료 콜백에서 수행해야 한다.

### 83. 오니기리 영구 강화 Lv.1~4는 코인만 차감되고 아무 능력도 오르지 않는다

- 상점은 오니기리 Lv.1~4를 각각 `투사체 속도 +3%`, `+6%`, `+9%`, `+12%`로 판매한다.
- 영구 강화 공통 계산기는 이 문구를 발견하면 무기 객체의 `speed` 또는 `orbitSpeed`를 배율 적용한다.
- 그러나 오니기리 기본 객체에는 `speed`가 없고, 실행 컴포넌트도 무기 상태의 속도를 전달하거나 읽지 않는다.
- 실제 투사체 이동 속도는 `OnigiiriProjectile` 내부 상수 `SPEED = 11 / 8`로 고정돼 있다.
- Firebase 테스트 런타임에 영구 강화 레벨을 0→1→2→3→4로 넣어 계산한 결과, `permanentUpgradeLevel` 표식 외의 damage·cooldown·bounces·bounceRange·range·치명타 값이 모두 완전히 동일했다.
- 기존 영구 강화 테스트는 오니기리 Lv.5의 바운스 증가와 전체 Lv.10 결과만 확인하고 Lv.1~4 속도 변화를 검증하지 않는다.
- 영향:
  - 사용자는 네 단계 합계 2,800코인을 지불해도 발사체 이동·공격 주기·피해·바운스 중 어떤 성능도 얻지 못한다.
  - 느린 오니기리 이동 속도가 그대로라 추적 중 대상 소멸과 긴 체공시간도 개선되지 않는다.
  - 속도를 카탈로그의 정식 수치로 만들고 투사체에 전달하거나, 상점 문구와 효과를 실제 지원 능력으로 교체해야 한다.

### 84. 영구 강화 문구 파서가 이름이 다른 능력까지 함께 올려 일부 단계는 과적용·무효가 된다

- 영구 강화는 명시적 효과 데이터가 아니라 한국어 `summary` 문자열을 검색해 효과 종류와 최대 퍼센트를 역산한다.
- 범위 문구 하나를 발견하면 해당 무기의 `range`, `radius`, `zoneRadius`, `strikeRadius`, `lightLength`, `lightWidth`를 전부 같은 비율로 조정한다.
- 확인된 오적용:
  - 과학 플라스크 Lv.5 `웅덩이 범위 +10%`가 웅덩이뿐 아니라 투척 대상 탐색거리와 최초 폭발 반경도 +10% 올린다.
  - 보조배터리 미사일 Lv.10 `폭발 범위 +10%`가 폭발 반경뿐 아니라 적 탐색거리도 +10% 올린다.
  - 지우개 폭탄 Lv.1~4 `폭발 범위`가 투척 탐색거리까지 같이 올린다.
  - 학생용 랜턴 Lv.1~4 `빛 콘 길이`가 폭도 같이 올린다. Lv.4에서 길이와 폭이 이미 +8%가 되므로 Lv.5 `빛 콘 각도 +8%`를 구매해도 두 값이 그대로라 단계 전체가 무효다.
  - 오리요강 Lv.10 `스택 폭발 범위 +10%`가 별도 폭발 배율뿐 아니라 평상시 궤도 접촉 반경도 올린다.
- 쿨타임 파서도 `귀소 전환 시간`을 일반 공격 주기로 분류한다. 상어미사일 Lv.5는 표시상 귀소 전환만 -10%지만 실제로 발사 쿨타임 7000→6300ms, 재탐색 주기 300→270ms, 귀소 시작 배율 0.9를 동시에 적용한다.
- 단계별 재현에서 랜턴 Lv.4와 Lv.5의 `lightLength=2.246`, `lightWidth=3.888`이 완전히 동일했고, 상어미사일 Lv.5의 표시되지 않은 cooldown 감소도 확인됐다.
- 기존 테스트는 최종 객체의 일부 과적용 값을 기대값으로 고정해 오히려 잘못된 동작을 정상으로 승인하며, 각 문구가 허용된 단일 능력만 바꾸는지는 검사하지 않는다.
- 영향:
  - 상점 설명만 보고는 실제 DPS·범위·안전성이 얼마나 오르는지 알 수 없다.
  - 일부 무기는 같은 가격으로 여러 능력을 받고, 랜턴 Lv.5처럼 아무 효과도 못 받는 단계가 생겨 무기별 경제가 불공정하다.
  - 문자열 파싱을 제거하고 단계별 구조화 효과 필드와 허용 대상 스탯을 명시해야 한다.

### 85. 후반 레벨업 카드 풀이 한 장으로 고갈되고 최대 체력을 무제한 누적한다

- 카드 UI는 `pickThree()`로 최대 세 장을 제시하지만 사용 가능한 후보가 세 장 미만일 때 대체 후보나 반복 가능 성장 규칙을 만들지 않는다.
- 보유 무기 상한 8개에 도달하면 나머지 무기 획득 카드는 모두 차단되고, 각 보유 무기가 Lv.5면 해당 무기의 모든 강화 카드도 차단된다.
- 이동속도가 기본속도의 1.8배 상한에 도달하면 이동 카드도 제거되지만 `maxHealth`에는 횟수·레벨·최대 HP 상한이 전혀 없다.
- Firebase 테스트 런타임에서 8개 보유 무기를 모두 Lv.5, 나머지 무기를 해금 상태, 이동속도를 상한으로 구성해 전체 58개 효과를 평가한 결과 사용 가능 후보는 `maxHealth` 한 장뿐이었다.
- 이후 레벨마다 선택지는 사실상 고정되고 최대 HP와 현재 HP가 매번 20씩 끝없이 증가한다.
- 이 문제는 240초 이후에도 런이 끝나지 않는 81번 문제와 결합해 장기 카이팅 플레이어가 계속 체력을 축적하는 생존 스노우볼을 만든다.
- 과거 중간점검 문서도 “후반 카드가 3개 미만”인 위험을 지적했지만 현재 테스트에는 최대 무기 수·전 무기 Lv.5·이동 상한 조합이 없다.
- 영향:
  - 선택형 성장 UI가 후반에는 선택이 아닌 단일 확인 버튼이 된다.
  - 무한 생존 랭킹에서 시간이 길어질수록 플레이어가 오히려 죽기 어려워져 정상 240초 점수와 격차가 더 커진다.
  - 세 후보를 유지할 반복형 대체 카드, 체력 상한 또는 최대 성장 후 레벨업 종료 규칙을 명시해야 한다.

### 86. 스테이지 3 런좀비 크루는 경계벽에 막혀 퇴장 조건에 도달할 수 없다

- RZL·RZC 런좀비는 플레이어를 추적하지 않고 정해진 대각선 방향으로 화면을 가로지른 뒤 사라지는 이벤트로 구현돼 있다.
- 제거 조건은 적 중심이 `mapHalfX + 6` 또는 `mapHalfZ + 6`보다 바깥으로 나가는 것이다.
- 그러나 `Floor.jsx`는 정확히 `±mapHalfX`, `±mapHalfZ`에 두께 1의 fixed 물리 벽을 만들고, 런좀비는 별도 충돌 그룹이 없는 dynamic body라 이 벽과 정상 충돌한다.
- 런좀비는 벽을 통과할 수 없으므로 제거선까지 추가 6유닛을 이동할 수 없다. 대각선 속도를 계속 벽 쪽으로 설정하다 결국 경계나 모서리에 눌린 채 남는다.
- 스테이지 3에는 35·80·120·150초에 각각 13개씩 총 52개의 런좀비가 예약돼 있어, 플레이어가 모두 처치하지 않으면 이전 이벤트 개체가 다음 이벤트와 누적된다.
- 남은 개체는 `enemyBodies`와 React/물리 객체에 계속 존재하고 무기 자동 타깃 후보에도 남는다.
- 기존 테스트는 13개 대형의 좌표·리더 수·방향과 일정만 검사하며 실제 경계벽 충돌 후 언마운트되는지 시뮬레이션하지 않는다.
- 영향:
  - “화면을 가로질러 지나가는 일회성 압박”이 가장자리 고정 적 무리로 변한다.
  - 자동 조준 무기가 화면 밖·모서리의 런좀비를 계속 선택해 현재 위협에 대한 화력이 낭비될 수 있다.
  - 최대 52개의 불필요한 dynamic body와 시각 레지스트리가 후반 성능 저하를 키운다.
  - 런좀비만 경계벽과 충돌하지 않게 하거나, 벽에 닿은 시점/맵 안쪽 종료선에서 안전하게 제거해야 한다.

### 87. 그래픽 스타지오의 `XP Orb`는 실제 게임에 존재하지 않는 유령 편집 항목이다

- 그래픽 스타지오 카탈로그는 `pickup-xp-orb`를 Gold Coin·XP Textbook·회복 아이템과 같은 정식 픽업으로 노출하고 `components/XpOrb.jsx`를 Apply 대상으로 지정한다.
- `GraphicsStudioPreview`도 XP Orb 모델을 정상 렌더하므로 관리자는 실제 게임 요소라고 인식하고 외형을 편집할 수 있다.
- 그러나 최신 XP 정본은 적 처치 시 교과서를 드랍하는 방식이며, 실제 게임 트리와 `Enemies`에는 `XpOrb` 상태·생성·렌더 경로가 전혀 없다.
- 전체 운영 소스에서 `XpOrb`의 유일한 마운트는 그래픽 스타지오 프리뷰뿐이다.
- 따라서 Firebase에 XP Orb 튜닝을 Apply해도 실제 스테이지에서 그 결과가 나타날 대상이 없다.
- 영향:
  - 관리자는 저장과 Apply가 성공한 것처럼 보이지만 게임에서는 영원히 확인할 수 없는 작업을 하게 된다.
  - “스타지오에서 Apply한 것은 게임에 즉시 적용”된다는 핵심 계약이 카탈로그 수준에서 깨진다.
  - 폐기된 XP Orb 항목을 스타지오에서 제거하거나 실제 게임 요소로 복구하고, 모든 스타지오 항목에 런타임 소비처가 존재하는지 자동 검증해야 한다.

### 88. 교과서와 골드 픽업은 수명·최대 개수 제한이 없어 계속 누적된다

- `XpTextbook`과 `GoldCoin`에는 획득 전 자동 소멸 시간, 맵별 최대 개수, 오래된 항목 교체 규칙이 없다.
- `Enemies`의 `textbooks`·`goldCoins` 배열도 새 항목을 계속 추가할 뿐 길이를 제한하지 않는다.
- 일반 적은 30% 확률로 교과서를 만들고, 시간제 골드·엘리트·보스·도지 상자도 추가 픽업을 생성한다.
- 도달 불가능한 위치 문제(77번)로 수집하지 못한 항목은 런이 끝날 때까지 영구 잔존한다.
- 골드 한 개는 본체 외에 SparkleParticle 6개를 마운트한다. 반짝임은 0.32초 후 `visible=false`가 될 뿐 컴포넌트와 `useFrame` 콜백은 코인을 수집할 때까지 계속 남는다.
- 교과서도 개체마다 프레임 콜백과 여러 재질·메시를 보유한다.
- 240초 종료가 강제되지 않는 81번 문제와 결합하면 픽업 수와 프레임 콜백은 이론상 무제한 증가한다.
- 영향:
  - 픽업을 일부러 회수하지 않는 장기 런에서 React 노드·재질·프레임 콜백·메모리가 계속 증가한다.
  - 저사양 Android의 후반 프레임 저하가 플레이어의 수집 행동과 난수 착지 위치에 따라 크게 달라진다.
  - 도달 가능한 착지 보장과 함께 픽업 풀링, 안전한 최대 개수, 게임 시간 기준 수명 정책을 도입해야 한다.

### 89. 공격력·학습력·자석 패시브가 표시된 퍼센트대로 단계별 효력을 내지 않는다

- `buildInitialWeapons()`는 패시브 유무와 관계없이 모든 무기 피해를 소수 첫째 자리로 반올림한다.
- 이 때문에 카탈로그상 랜턴 기본 피해 `0.15`는 패시브 Lv.0에서도 `0.2`가 돼 이미 +33.3% 변하고, 치비코 `1.25`도 `1.3`으로 변한다.
- 공격력 패시브는 레벨당 +4%지만 연필은:
  - Lv.0: 1.5
  - Lv.1: 1.6(실제 +6.7%)
  - Lv.2: 1.6(추가 구매 효과 0)
  - Lv.3: 1.7
- 랜턴은 Lv.0~Lv.3 모두 반올림 결과가 `0.2`라 공격력 패시브 세 단계가 전부 실전 피해를 전혀 올리지 않는다.
- 학습력은 교과서 하나를 먹을 때마다 `floor(amount * multiplier)`로 소수 XP를 즉시 버린다. XP 5·6 교과서는 학습력 Lv.1~3 모두 원래와 같은 5·6 XP이고, XP 10도 Lv.1에서는 그대로 10이다.
- 자석 기획 정본은 기본 흡입 반경 0.75에서 레벨당 +8%라고 설명하지만, `applyMagnetPassive()`는 미구매 시 배율을 0으로 설정한다. 실제 반경은 Lv.0 `0` → Lv.1 `0.81`로 갑자기 활성화돼 “+8%”가 아니다.
- 기존 테스트는 공격력 Lv.2의 1.62가 1.6으로 반올림되는 값을 정상 기대치로 고정하고, 학습력은 효과가 보이는 큰 XP 20만 사용해 저XP 무효를 피한다.
- 영향:
  - 같은 가격의 패시브 레벨이 무기·교과서 값에 따라 과효율 또는 완전 무효가 된다.
  - 사용자는 상점의 +4%·+5%·+8% 문구로 실제 변화를 예측할 수 없다.
  - 내부에 충분한 정밀도로 누적한 뒤 표시만 반올림하고, 학습력의 소수 XP 누적 버퍼와 자석 기본 반경 정본을 복구해야 한다.

### 90. 그래픽 스타지오의 스폰 연기·스타링크 충돌 이펙트 Apply가 실제 게임에 반영되지 않는다

- 카탈로그는 `vfx-zombie-spawn-puff`와 `weapon-starlink-crash-impact`를 정상 편집 항목으로 노출하고 Firebase 튜닝 저장 대상에 포함한다.
- 스튜디오 미리보기는 선택 항목 전체를 현재 튜닝의 위치·회전·스케일로 감싸므로 두 항목 모두 편집 결과가 화면에 보인다.
- 실제 게임의 `SpawnSmokeEffect`는 `StudioTunedGroup`이나 `vfx-zombie-spawn-puff`를 전혀 읽지 않고 원본 `Billboard`를 직접 렌더한다.
- 실제 게임의 `CrashExplosionVisual`도 `weapon-starlink-crash-impact`를 읽지 않고 일반 `group`과 고정 메시만 렌더한다.
- 반면 같은 스타링크 추락 시퀀스의 낙하 위성은 `weapon-starlink-crash-fall`, 도주 캐릭터는 `actor-zomlonbisk` 튜닝 그룹을 실제로 소비하므로 충돌 이펙트만 연결이 끊겨 있다.
- `GraphicsStudioPreview.test.js`의 “catalog-only studio items wired to runtime tuning groups” 테스트는 바닥·체력바·E04 탄환·일부 VFX·사망 연출만 검사하며 이 두 카탈로그 항목은 검사하지 않는다.
- 영향:
  - 관리자는 스튜디오에서 Apply 성공과 변경된 미리보기를 확인하지만 게임의 좀비 등장 연기와 스타링크 충돌 이펙트는 이전 모습 그대로다.
  - Firebase에는 실제 소비자가 없는 값이 정본처럼 누적되어 Studio·게임 즉시 동일성 계약을 위반한다.
  - 카탈로그의 모든 항목을 실제 런타임 `itemId` 소비처와 자동 대조하고, 소비자가 없는 항목은 연결 전까지 편집 대상에서 제거해야 한다.

### 91. 벨은 “8방향 파동”이 아니라 즉시 원형 범위 공격으로 동작한다

- 최신 영구강화 기획, 무기 목록, 획득 카드 설명은 벨을 `8방향 파동/충격파`로 정의한다.
- 무기 카탈로그도 `directions: 8`, `speed: 10`을 기본 능력으로 보유한다.
- 실제 `BellShockwave`는 두 값을 어디에서도 읽지 않고 `applyRadialDamage()`를 한 번 호출해 현재 반경 안의 모든 적에게 즉시 피해를 준다.
- 화면의 여러 원형 링은 520ms 동안 퍼져 나가지만 순수 시각 효과이며, 링이 적에게 도달하는 시점과 피해 판정은 연결되지 않는다.
- 전체 소스에서 벨의 `directions` 소비처는 없고 `speed`도 벨 실행 코드에서 사용되지 않는다.
- 기존 벨 테스트는 넉백 상수 한 개만 확인하며 8개 방향, 파동 이동, 시각 링과 판정 도달 시각은 검증하지 않는다.
- 영향:
  - 카드 설명상 빈 방향 사이를 피할 수 있는 8개 파동처럼 보이지만 실제로는 원 안의 모든 적이 즉시 맞아 회피·타이밍·DPS가 다르다.
  - 방향 수와 속도를 향후 강화하거나 Studio/관리자 값으로 노출해도 현재 구조에서는 아무 효과가 없다.
  - 원형 충격파가 최종 의도라면 기획·카탈로그·카드에서 방향/속도 약속을 제거하고, 8방향 이동 파동이 의도라면 실제 투사체 판정과 시각 도달 시각을 연결해야 한다.

### 92. 우산 영구강화의 “넉백 +3~24%”는 힘이 아니라 밀리는 시간만 늘린다

- 최신 영구강화 기획과 상점은 우산 Lv.1~4·6~9를 `넉백 +3%`부터 `+24%`까지 판매하며, 의도를 방어·넉백 성능 강화로 설명한다.
- 우산 카탈로그의 넉백 값은 수치가 아닌 문자열 `strong`이고 실제 폭발 실행 코드는 이 값을 읽지 않는다.
- 실제 넉백 힘은 모든 강화 레벨에서 `knockback: 3.0`으로 고정돼 있다.
- 공통 한국어 문구 파서는 `넉백`을 발견하면 `knockbackMs`만 배율 적용한다. 따라서 Lv.9에서 힘은 여전히 3.0이고 밀리는 시간만 220ms→273ms가 된다.
- 기존 영구강화 테스트도 우산 최종값을 `knockbackMs: 273`으로 기대해, 설명과 다른 적용을 정상 동작으로 승인한다.
- 영향:
  - 플레이어가 기대하는 밀어내는 거리·순간 힘의 증가 대신 적이 같은 힘을 더 오래 받아 물리 결과가 프레임률·벽 충돌·다른 적 접촉에 더 민감해진다.
  - 상점의 퍼센트만으로 실제 방어 성능 변화를 예측할 수 없으며 아홉 단계의 구매 효과가 잘못된 능력에 적용된다.
  - `knockbackStrength`와 `knockbackDurationMs`를 구조화된 별도 능력으로 정의하고, 상점 문구가 가리키는 한 값만 단계별로 변경해야 한다.

### 93. 로비의 시즌 종료 카운트다운과 활성 상태가 진입 시각에 고정된다

- 로비는 `getActiveSeason()`을 `useMemo(..., [])`로 최초 마운트 때 한 번만 호출한다.
- `종료까지 N일 N시간` 또는 `N시간 N분` 문구도 렌더 시 `Date.now()`로 한 번 계산할 뿐, 시간을 갱신하는 interval이나 시즌 변경 구독이 없다.
- 골드·닉네임·모달처럼 다른 상태 변화가 우연히 리렌더를 일으키기 전까지 카운트다운은 같은 숫자에 멈춘다.
- 시즌 종료 시각을 지나도 `season.active`는 최초 객체 값 그대로이므로 로비를 나갔다 다시 들어오기 전까지 `시즌 준비중`으로 전환되지 않는다.
- 반대로 시작 전 로비를 오래 열어둔 경우에도 활성 시즌으로 자동 전환되지 않는다.
- 현재 `Lobby.test.jsx`는 쇼타임·터치 애니메이션 타이머는 검증하지만 시즌 카운트다운의 1분 경과나 시작·종료 경계 전환은 검사하지 않는다.
- 영향:
  - 플레이어가 실제보다 긴 잔여 시간을 믿고 랭킹 플레이를 시작할 수 있다.
  - 같은 화면의 시즌 표시와 서버 `submitRun()`이 각자 다른 현재 시각으로 활성 여부를 판단해, 로비에는 진행 중으로 보이지만 제출은 조용히 거부되는 순간이 생긴다.

### 96. Firebase 소품 목록의 중복 ID를 허용해 서로 다른 조사 대상이 하나로 합쳐질 수 있다

- `normalizePropPlacement()`는 비어 있지 않은 문자열 ID를 그대로 보존하고, `normalizeStagePropList()`는 각 항목을 정규화한 뒤 중복 여부를 검사하지 않는다.
- 렌더러와 Graphics Studio 편집기는 이 ID를 React `key`로 사용하며, 조사 시스템도 같은 ID를 런당 조사 완료 `Set`의 키로 사용한다.
- 따라서 Firebase 정본에 같은 ID를 가진 사물함·불레틴보드·학생이 둘 이상 들어오면:
  - React가 서로 다른 소품을 같은 항목으로 간주해 렌더·편집 상태를 잘못 재사용할 수 있다.
  - 먼저 발견된 한 대상을 조사하는 순간 같은 ID를 가진 다른 대상도 이미 조사한 것으로 처리된다.
  - 화면에 보이는 대상 수, 충돌체, 편집 선택, 조사 가능 횟수가 서로 불일치할 수 있다.
- 현재 `stagePropPlacements.test.js`에는 ID 중복 거부·재발급·fail-closed 동작을 검증하는 테스트가 없다.
- 이는 현재 기본 배치에서 중복 ID가 발견됐다는 뜻은 아니지만, 유일한 정본인 Firebase 입력을 신뢰 경계에서 검증하지 않는 확정적인 무결성 결함이다.
- Apply 전에 스테이지별 ID 유일성을 검증해 저장을 거부하고 명확한 오류를 표시하며, 읽기 경로도 중복 정본을 조용히 수용하지 말고 fail-closed 처리해야 한다.

### 102. Google 로그인 성공과 Firebase 진행도 hydrate 완료 사이에 게임 시작 경쟁 조건이 있다

- `signInWithGoogle()`은 Google 인증으로 사용자 객체를 받은 뒤 `syncCloudProgressUser(user)`를 호출하지만, 이 함수는 `hydrateCloudProgress()`를 `void` 비동기 작업으로 시작하고 즉시 반환한다.
- 따라서 로그인 Promise는 `progressStatus='loading'`인 동안에도 사용자 객체로 resolve된다.
- 타이틀 `handleStartClick()`은 로그인 반환 뒤 Graphics Studio 준비만 기다리고 플레이어 진행도의 `progressStatus` 또는 `isFirebaseProgressHydrated()`를 확인하지 않는다.
- `TitleScreen`과 `GoogleAccountPanel` 어느 쪽도 `progressStatus`·`progressError`를 구독하거나 로딩·재시도 UI로 표시하지 않는다.
- 느린 네트워크 또는 앱 재시작 직후 가능한 흐름:
  1. Google 인증 성공으로 화면은 로그인된 계정을 표시한다.
  2. 원격 진행도는 아직 hydrate 중이지만 게임 시작을 누를 수 있다.
  3. `getSavedNickname()`은 비어 있는 미hydrate 런타임을 읽어 기존 사용자를 닉네임 미설정으로 오판한다.
  4. 사용자가 닉네임을 제출하면 `updateFirebasePlayerProfile()`의 hydrate 가드가 예외를 던질 수 있다.
  5. 진행도 로드 실패도 타이틀에 표시되지 않아 사용자는 로그인과 게임 시작이 왜 막혔는지 알 수 없다.
- `ReadyGameApp.startGame()`에는 hydrate 가드가 있지만 이 경쟁은 그보다 앞선 타이틀→닉네임→로비 단계에서 발생한다.
- 현재 인증 테스트는 `hydrateCloudProgress()`가 호출됐는지만 기다리고, `signInWithGoogle()` Promise가 hydrate 완료까지 대기하는지 또는 UI가 loading/error를 차단하는지는 검사하지 않는다.
- 로그인 완료 조건을 “Auth 사용자 확보 + 동일 UID 진행도 hydrate 성공”으로 원자화하고, loading 중 시작 버튼 비활성화와 실패 재시도·오류 표시를 제공해야 한다.

### 103. 타이틀을 벗어난 모든 실제 게임플레이에 BGM이 없다

- 저장소 전체의 오디오 생성·재생 소비처를 대조한 결과 BGM은 `TitleScreen.jsx`의 `title_bgm.m4a` 한 개뿐이다.
- 로비·Stage 1~4·보스전·게임오버에는 배경음악 재생기, 스테이지 트랙 매핑, 전환·페이드 코드가 없다. 전투 중에는 무기·적·UI 효과음과 짧은 대화 합성음만 재생된다.
- Sound_Mini 방향 문서는 저용량 BGM 2~3개와 짧은 루프를 기본 범위로 제시하고, 효과음 파라미터 문서도 결과음이 전투 BGM 위에서 읽혀야 한다고 전제한다.
- 따라서 타이틀에서 게임을 시작하는 순간 음악이 완전히 끊기며, 240초 스테이지·보스 등장·클리어로 이어지는 긴 플레이의 긴장도와 구간 구분이 효과음에만 의존한다.
- 스테이지별/공용 전투 BGM의 최소 구성을 확정하고 사용자 제스처 기반 AudioContext 해제, pause·백그라운드·결과 화면 전환, BGM/SFX 분리 음량을 함께 설계해야 한다.

### 104. Google 로그인 진행 중에도 타이틀 BGM이 계속 재생된다

### 105. 로그아웃·인증 해제 시 이전 사용자의 게임 메모리가 남고 진행 중 화면도 종료되지 않는다

### 106. 종료된 적 등장 연기가 살아 있는 적마다 프레임 콜백을 계속 유지한다

- 모든 `Enemy`는 생존 기간 내내 `SpawnSmokeEffect`를 렌더한다.
- 등장 연기는 `SPAWN_SMOKE_DURATION_MS`가 지나면 `useFrame` 안에서 React state `done=true`를 설정하고 이후 `return null`로 메시만 숨긴다.
- 그러나 `return null`은 `SpawnSmokeEffect` 컴포넌트를 unmount하지 않는다. 내부 `useFrame` 구독은 적이 죽어 부모 `Enemy`가 제거될 때까지 계속 호출되며, 사라진 `billboardRef`·`materialRef`를 확인하고 매 프레임 반환한다.
- 결과적으로 한 웨이브에서 40마리가 살아 있으면 시각적으로 끝난 연기 콜백도 40개가 계속 남는다. 처치가 밀리거나 87번의 런좀비가 경계를 통과한 뒤 잔존하면 불필요한 구독이 계속 증가한다.
- 이는 프로젝트 안정성 규칙의 “프레임 콜백에서 React state 갱신 금지”에도 직접 어긋난다. 연기 완료 순간 `setDone(true)`가 렌더 스케줄을 발생시킨다.
- 적 렌더 테스트는 연기 지연·pause 타이머 문구와 모델 구조를 검사하지만, 연기 종료 후 실제 `useFrame` 구독 수가 감소하는지 측정하지 않는다. 500런 스트레스 테스트도 store 함수만 반복하고 R3F 트리를 렌더하지 않는다.
- 연기 수명을 부모 또는 중앙 이펙트 풀에서 관리해 완료 즉시 컴포넌트를 실제 unmount하고, 대량 웨이브 전후 R3F subscriber 수와 프레임 비용이 원상 복구되는지 검증해야 한다.

### 109. Google 로그인 UI가 개발 환경명과 원시 영문 오류를 사용자에게 노출한다

- `GoogleAccountPanel`은 Firebase 설정이 없을 때 일반 사용자에게 `Firebase .env 설정 필요`를 그대로 표시한다.
- `.env`는 개발자가 빌드 환경변수를 넣는 내부 파일명이다. 플레이어가 해결할 수 없는 구현 세부사항이며 프로덕션 설정 누락을 사용자 안내처럼 노출한다.
- 인증 예외는 `getErrorMessage()`가 `error.message`를 가공 없이 반환하고 패널이 그대로 렌더한다. 따라서 다음과 같은 SDK·플랫폼 원문이 한국어 UI에 나타날 수 있다.
  - `auth/popup-closed-by-user`
  - `auth/network-request-failed`
  - `DEVELOPER_ERROR`
  - `Mobile Google login failed.`
  - fallback `Google login failed.`
- 사용자 행동이 필요한 취소·네트워크·계정 선택과 운영자가 고쳐야 하는 설정·OAuth 구성 오류가 하나의 `로그인 오류` 상태로 합쳐져 있다. 재시도 가능 여부, 네트워크 확인, 앱 업데이트·문의 같은 다음 행동도 구분하지 않는다.
- 진행도 hydrate 실패는 102번처럼 패널에 아예 나타나지 않으므로, 인증 단계는 원시 오류를 과도하게 보여주고 진행도 단계는 오류를 숨기는 반대 방향의 불일치를 가진다.
- 현재 테스트는 `unconfigured` 패널이 렌더되는지만 확인하고 개발 문자열 비노출, Firebase 오류 코드의 한국어 매핑, 재시도 CTA를 검증하지 않는다.
- 내부 오류는 로그에만 보존하고 UI에는 취소·네트워크·설정·진행도 로드 실패를 안정된 한국어 메시지와 다음 행동으로 매핑해야 한다. 프로덕션 설정 누락은 플레이어 화면이 아니라 릴리스 빌드 게이트에서 차단해야 한다.

### 110. 점수에 영향을 주는 런 난수가 시드·로그 없이 전역 `Math.random()`에 흩어져 있다

- 실제 플레이 결과에 영향을 주는 난수 소비처가 하나의 런 RNG로 통합돼 있지 않다.

## 검증 한계

- 실제 Google OAuth는 자동 브라우저에서 실행하지 않았다.
- 실제 Firebase 데이터는 테스트 전후 동일성 정책 때문에 변경하지 않았다.
- E2E 진입 결함으로 스테이지 1~4의 실제 4분 완주 테스트를 수행할 수 없었다.
