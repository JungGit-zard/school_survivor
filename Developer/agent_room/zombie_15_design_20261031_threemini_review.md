## 1. 얼굴 실제 크기 재계산 (§3 가독성 경고와 §4.4 Q1)

`[코드 확인]`

- 카메라: `GameCanvas.jsx`에서 `fov 30`, `position [0,17,17]`, `near 0.1`, `far 500`
- **DPR: `dpr={[1, 1.5]}`**. 장치 DPR이 2.75여도 렌더 해상도는 **1.5배로 잘린다.** 문서의 "장치 픽셀 약 30px(DPR 2.75)"는 성립하지 않는다.
- `gl={{ stencil: true }}`만 덮어쓰므로 R3F 기본값 `antialias: true`(MSAA)가 살아 있다. `EffectComposer`나 후처리는 쓰지 않는다.
- 좀비 표시 스케일 0.333, POSED 머리 베이스 `0.52×0.48×0.46`, 머리 박스는 RoundedBox 1세그먼트 챔퍼(반경 = 최소축 × 0.14 ≈ 0.064)다.

`[계산]` 세로 화면 높이를 800 CSS px로 가정했다.

| 항목 | 값 |
|---|---|
| 카메라와 플레이어 사이 거리 | √(17²+17²) ≈ 24.0u |
| 그 거리의 세로 시야 | 2 × 24.0 × tan15° ≈ 12.9u → 약 62 CSS px/u |
| 머리 앞면 폭 | 0.52 × 0.333 = 0.173u → **약 10.7 CSS px** |
| 머리 앞면 높이 | 0.48 × 0.333 = 0.16u. 45°로 내려다보므로 cos45°를 곱해 0.113u → **약 7 CSS px** |
| 장치 픽셀(DPR 1.5) | **약 16 × 10.5 px** |
| UV 1.0당 장치 px | 가로 약 16px, 세로 약 10.5px |

문서는 45° 원근 축소(세로 ×0.707)와 DPR 상한을 모두 빠뜨렸다. 세로 해상도는 문서 추정의 약 1/3이다. 화면 위쪽 좀비는 더 멀어서 ±25% 정도 더 작아진다.

**결론(Q1)**: 문서의 "선 두께 0.025, 원 반경 0.03" 기준으로는 부족하다. E07의 입선(반폭 0.018, 전체 0.036)도 세로로 0.4 장치 px밖에 안 되어 지금도 거의 깜빡이는 흐린 선으로만 보일 것이다(`[계산]`, 실기 확인 필요).

### 1.1 얼굴 쿼드를 머리보다 키울 것인가 (×1.3)

- **쿼드만 머리 밖으로 키우는 것은 반대한다.** 아웃라인은 머리 헐에만 걸린다. 그래서 머리 실루엣 밖으로 삐져나온 이목구비는 외곽선 없는 스티커처럼 뜬다. 챔퍼 모서리에서는 쿼드가 둥근 면 앞에 떠서 비스듬히 볼 때 틈이 보인다.
- `[권고]` 대신 얼굴형 15종은 **머리 박스 자체를 ×1.25~1.3**으로 키운다(리그의 `head.scale`). 카툰 큰머리 비례가 되고, 아웃라인과 그림자가 함께 따라온다. 얼굴 쿼드는 **머리 앞면의 평탄부 안**에 둔다(평탄부 ≈ 폭과 높이의 약 73~75%. 이목구비 범위는 UV 0.13~0.87 안).
- 머리 ×1.25를 적용하면 얼굴은 약 13×9 CSS px, 장치 약 20×13px가 된다. 이 크기가 설계 기준이다.

## 2. §4.4 질문 7개 답변

### Q1. 공용 얼굴 InstancedMesh가 기존 `ZombieInstanceLayer`와 맞는가: 머리 포즈 동기, 아웃라인과 z-fighting, 정밀도

방향은 맞다. 단, 다음 조건을 지켜야 한다.

**머리 포즈 동기** `[코드 확인]`: 인스턴스 경로에서 머리 행렬은 한 체인으로 만들어진다. 순서는 `m = compose(pos, yaw, scale) × studioRoot` → `× T(pivot + Studio 오프셋)` → `× R(setPartRotation + Studio 회전 + 리그 pose 델타 + statePose)` → `× S(Studio 스케일)` → `× T(offset)` → `× S(part.box)`이다. 포즈형은 `setPartRotation`의 `head`가 z축으로 흔들리고(`sin(t×1.6)×0.07`), 예고와 회복 상태 포즈도 더해진다.

- `[권고]` 얼굴 행렬은 **같은 j 루프 안에서 head 슬롯(j=0)을 계산할 때, box 스케일을 곱하기 직전의 `a`를 복사해서** 만든다. `face = a × T(0, 0, 0.23 × box.z + ε) × S(0.52 × box.x × k, 0.48 × box.y × k, 1)`. 이렇게 하면 Studio 머리 튜닝, 상태 포즈, 비균등 머리 비례가 전부 자동으로 따라온다. 별도 레이어에서 포즈를 다시 계산하면 반드시 어긋난다(E34~E45가 직전에 겪은 상태 코드 누락과 같은 종류의 버그다).
- 이 계산은 순수 함수 `composePooledFaceMatrix(out, headMatrixBeforeBox, headBox, k, eps)`로 빼서 테스트한다.
- 머리 비례가 비균등(`box.x ≠ box.y`)하면 원이 타원으로 늘어난다. 셰이더 좌표를 `p = (uv - 0.5) × vec2(w/h, 1)`로 등방화하고, 종횡비를 attribute로 넘긴다.
- **얼굴형 종은 eye 박스 슬롯(1, 2)을 반드시 끈다.** 눈 박스는 z 0.24 + 깊이 0.06으로 머리 앞면 밖에 0.03 튀어나온다. 그대로 두면 얼굴 쿼드를 가린다.

**아웃라인과 z-fighting** `[코드 확인]`: 아웃라인은 BackSide 헐(스케일 `1+(s-1)×2`)이고, 스텐실 NotEqual 1, `transparent`, `depthWrite false`, renderOrder 1이다. 몸통 툰 재질은 스텐실 1을 쓴다.

- 얼굴 쿼드에는 헐을 만들지 않는다(당연한 조건).
- ε는 머리 로컬 0.006(월드 약 0.002u)을 권한다. `[계산]` near 0.1, 24bit 깊이, 거리 24u에서 깊이 분해능은 약 0.00034u라서 6배 여유가 있다. 안전을 위해 `polygonOffset: true, factor -1, units -4`를 함께 쓴다.

**WebGL1과 mediump** `[코드 확인]`: `three ^0.164.1`이다. three는 r163부터 WebGL1 지원을 없앴다. **WebGL1은 대상이 아니다.** ShaderMaterial은 렌더러 capability에 따라 `precision highp`가 자동으로 붙고, ES3 프래그먼트 셰이더는 highp를 지원한다.

- `int(aFaceId + 0.5)` 캐스팅도 문제없다. 쿼드 안에서 같은 값이므로 varying 보간 오차도 없다.
- 남는 정밀도 리스크는 `uTime`뿐이다. 앱 시작 이후 누적되는 값이라 몇 시간이 지나도 float32로 충분하지만, 주기를 맞춰 `mod`로 감싸 두기를 권한다.

### Q2. 분기 셰이더 1개 vs 변형 15개, 컴파일 지연과 프리웜

`[권고]` **분기 셰이더 1개(1 드로콜)**를 쓴다.

- 프래그먼트 비용은 무시할 만하다. 얼굴 1개는 약 20×13 장치 px ≈ 260 프래그먼트이고, 40기면 약 1만 프래그먼트다. 일부 모바일 컴파일러가 분기를 펼쳐서 15개 얼굴을 모두 계산해도 프레임당 수십 MFLOP 수준이다. 다만 **얼굴 1개당 SDF 프리미티브를 12개 이하**로 제한해 이 최악의 경우를 막는다.
- 변형 15개는 컴파일 15회, 드로콜 15회, 프로그램 전환 15회가 필요하다. 총 컴파일 시간은 오히려 더 길다.
- 실측에서 저가 기기 첫 컴파일이 150ms를 넘으면 5종씩 묶어 3변형으로 나눈다.

**프리웜 함정** `[코드 확인]`: `StageEntryRuntimeDiagnostics.jsx`가 게임 Canvas에서 `gl.compileAsync(scene, camera)`를 한 번 호출한다. three r164의 `compile`과 `compileAsync`는 **`scene.traverseVisible`로 보이는 객체만** 컴파일한다. 그런데 `ZombieInstanceLayer`의 `markInstancedMeshFullUpdate`와 `PrefixUpdate`는 `x.visible = count > 0`으로 둔다. 리셋 직후 count가 0인 인스턴스 메시는 **프리웜 대상에서 빠진다.**

- `[권고]` 얼굴, 소품, 신규 투사체, 예고 데칼 인스턴스 메시는 **항상 `visible=true`로 두고 count만 0으로** 만든다(count 0이면 그리지 않는다). 아니면 프리웜하는 동안만 강제로 보이게 한다. 개발 지표(`stageEntryMetrics`의 `gl.info.programs`)에 얼굴 프로그램이 들어 있는지를 수락 기준으로 둔다.
- 참고로 기존 인스턴스 툰 프로그램도 같은 이유로 프리웜에서 빠지고 있을 가능성이 있다. 이번 범위가 아니므로 보고만 한다.

### Q3. 얼굴 InstancedMesh를 `ZombieInstanceLayer` 안에 넣을 것인가, 별도 레이어로 둘 것인가

`[권고]` **`ZombieInstanceLayer` 안에 넣는다.** 다음 값을 모두 같은 루프에서 공유해야 하기 때문이다.

- `bodyVisible`: `spawnTimer >= SPAWN_REVEAL_MS`. "펑" 300ms 공개 규칙이다.
- 렌더 티어: 얼굴은 NEAR와 MID에서만 그리고 FAR(11u 초과)에서는 끈다. 기존 eye 박스는 MID에서 꺼지지만, 얼굴은 식별 정체성이므로 MID까지 유지한다.
- 피격 플래시(`hitFlashTimer`): 몸통이 흰색이 될 때 얼굴도 같이 반응하게 플래그로 넘긴다.
- 그림자와 체력바 슬롯 순서, 리셋(`resetKey`) 때 행렬 0 처리

별도 레이어로 두면 이 다섯 조건을 복제해야 하고, 머리 행렬을 다시 계산해야 한다.

- per-instance 값은 문서처럼 4개 float로 따로 두지 말고 **vec4 `aFace`(id, phase, state, misc) 하나**로 묶는다. 업로드가 1회로 줄어든다.
- 종횡비와 플래시 값이 필요하면 vec2 하나를 더 쓴다.
- 용량은 64가 아니라 **`POOLED_ENEMY_CAPACITY` 200**으로 둔다. 메모리는 미미하고, 넘친 좀비가 얼굴 없이 그려지는 상태(눈 박스를 껐으므로 얼굴이 아예 없다) 자체를 없앤다.

### Q4. E07을 faceId 0으로 옮길 것인가

`[권고]` **옮기지 않는다.**

- E07은 `StudioTunedGroup itemId="zombie-procedural-face-test"`의 공유 박스 트리 6파트(머리 0.56×0.5×0.48, 비챔퍼 박스, 자체 보행 포즈)에 Studio 튜닝이 걸려 있다. 인스턴스 POSED 체인으로 옮기면 Studio 값이 붙는 모델 트리 자체가 바뀐다.

- 옮기려면 Terry 승인과 Studio 값 매핑 검증 계획이 따로 필요하다(문서 §7 질문 7의 답으로 "보류"를 권한다).

### Q5. 좀비가 옆이나 뒤를 볼 때 얼굴 처리

`[권고]` **아무 처리도 하지 않는다.** 깊이 테스트로 자연스럽게 가린다. 빌보드나 윗면 쪽으로 기울이는 방식은 반대한다.

- 카메라는 +Z 쪽에 있다. 플레이어보다 화면 위쪽(−Z)에 있는 추격 좀비는 카메라를 향하고, 아래쪽 좀비는 등을 보인다. 그래서 **어느 순간에나 약 절반의 좀비만 얼굴이 보인다.**
- 기울인 평면은 머리 박스 안으로 파고들거나 머리 밖으로 튀어나온다. 빌보드는 "몸은 옆인데 얼굴은 정면"이 되어 카툰 3D 정책과 충돌한다.
- **따라서 얼굴은 텔레그래프의 단독 채널이 될 수 없다.** 문서 §1.4의 3채널 원칙이 맞고, (a) 몸 포즈와 (c) 바닥 지시가 필수다. 얼굴은 보너스 채널이다. balanceqa의 회피 가능성 테스트도 얼굴 채널을 빼고 통과해야 한다.

### Q6. alphaTest discard와 소프트 알파 중 무엇인가

`[권고]` **소프트 알파 블렌딩**(`transparent: true, depthWrite: false, depthTest: true`)을 쓴다. 문서 권고와 반대다.

- 문서가 걱정한 "인스턴스 간 정렬 불가"는 여기서 문제가 되지 않는다. 모든 얼굴은 **자기 머리(불투명, depth 기록) 바로 앞에** 있다. 앞에 있는 다른 좀비의 머리와 몸은 depth로 뒤쪽 얼굴을 가린다. 얼굴끼리 순서가 꼬일 수 있는 영역이 사실상 없다.
- alphaTest 0.5는 1~2px 크기의 이목구비를 이진화한다. 좀비가 흔들리고 움직일 때 선이 생겼다 사라지는 **크롤링**이 생긴다.
- alphaToCoverage는 MSAA가 켜져 있어서(R3F 기본 `antialias`) 쓸 수는 있다. 그러나 MSAA를 무시하는 WebView에서는 alphaTest와 같아지므로 1순위가 아니다.
- **renderOrder는 0.5**를 권한다. 투명 리스트에서 아웃라인(1)보다 먼저 그리면, 앞쪽 좀비의 아웃라인이 뒤쪽 얼굴을 올바르게 덮는다. E07처럼 3으로 두면 뒤쪽 얼굴이 앞쪽 좀비의 외곽선 위에 칠해진다. 같은 얼굴 위로 아웃라인이 오는 일은 스텐실 1과 depth가 막는다.
- **AA 방식을 바꾼다.** E07의 `softCircle`은 정규화 제곱거리를 쓰고, `softLine`은 smoothstep(0.7w, w)를 쓴다. 둘 다 반경에 비례하는 고정 AA라서 작은 화면에서는 AA 폭이 1px 미만으로 줄어 계단이 생긴다. 신규 모듈은 UV 단위 실거리 SDF에 `fwidth` 기반 AA를 쓰고, **최소 획 픽셀 클램프** `width = max(width, 0.75 × fwidth(d))`를 넣는다. 그러면 먼 좀비에서도 선이 사라지지 않고 굵어지기만 한다. 이 처리가 이번 가독성 문제의 핵심 해법이다.

### Q7. 신규 투사체를 kind 분기로 넣을 것인가, 형태별 InstancedMesh로 묶을 것인가

`[권고]` **새 `NovelProjectileLayer`에 형태 클래스별 InstancedMesh를 둔다.**

- `PooledEnemyProjectileLayer`는 kind마다 InstancedMesh 쌍(body + BackSide 외곽선)을 두고, B04 재료는 병합 지오메트리에 vertexColors를 쓴다. kind 0(E04)은 정본이라 변경할 수 없다. 신규 풀은 어차피 별도 SoA이므로 레이어도 분리한다.
- 형태 클래스는 **box / sphere(저폴리) / cone(4면)** 3종이다. `instanceColor`와 per-instance 비균등 스케일, 속도 방향 쿼터니언을 쓴다. 툰 + 외곽선이라 **6 드로콜 고정**이다. 음표(구 + 막대)와 우유갑(상자 + 지붕)처럼 복합 형태는 투사체 1발에 인스턴스 2개를 쓴다.
- 지시선, 점선 반사 경로, 귀환 타원, 착탄원, 퓨즈원, 링 6눈금, 조준선, 웅덩이, 음파 띠는 **SDF 예고 데칼 InstancedMesh 1개**(얼굴과 같은 패턴. per-instance shapeId와 파라미터)로 통합한다. 투명 지대를 별도로 두더라도 +1이다. 바닥 데칼 선 폭은 **0.06u(약 4 CSS px) 이상**으로 한다.

## 3. 15종 몸통, 소품, 투사체: 박스 파이프라인 적합성과 비용

### 3.1 전제가 되는 파이프라인 사실 `[코드 확인]`

- 인스턴스 경로의 `im()`은 **챔퍼 박스(RoundedBoxGeometry)만** 만든다. 원기둥, 원뿔, 구, 토러스, 이코사헤드론은 이 파이프라인에 없다.
- 슬롯 구조: `ALL_PARTS` 94슬롯이 슬롯마다 body와 outline InstancedMesh 2개를 가진다. count가 0보다 큰 슬롯만 그린다.
- POSED 13슬롯 세트(E34~E45)는 박스 크기가 고정이고 종별 비례는 `part.box` 스케일로만 표현한다. `ZombieMesh.jsx` 주석이 "옷, 소품, 무기, 추가 장식 파츠는 만들지 않는다", "표식은 자체 기울기를 두지 않는다(공유 트리는 행렬 곱, 인스턴스는 오일러 합이라 어긋난다)"를 설계 규칙으로 못 박고 있다.
- 따라서 문서 §4.2의 "몸통은 기존 배치에 합류(+0~2)"는 **소품이 없는 경우에만** 맞다.

### 3.2 반드시 필요한 기반 확장

1. **POSED 슬롯 확장**: 얼굴형은 eye 2슬롯을 끄고, **박스 소품 슬롯 K=3**을 추가한다. 슬롯 1개를 쓸 때마다 +2 드로콜이다.
2. **소품 로컬 회전 지원**: X자 자, 기울어진 확성기, 지붕 우유갑 등에 필요하다. 공유 박스 트리(Studio, 프리뷰)와 인스턴스 경로 **양쪽에** 같은 합성 순서 `T(offset) × R(local) × S(box)`를 넣고, 두 경로의 월드 행렬이 같은지 확인하는 패리티 테스트를 둔다.
3. **비박스 형태 클래스 3종**: cylinder 8면, cone 4/8면, sphere 저폴리. 단위 지오메트리 1개를 비균등 스케일로 재사용하고, 툰 + 아웃라인으로 +6 드로콜이다. 특정 슬롯에 묶이지 않는 공용 풀(용량 약 400)로 둔다. 볼록 형태라 인버티드 헐 아웃라인과 스텐실이 그대로 동작한다.
4. **`phase()` 상태 코드 매핑**: 문서 §1.6의 "`phase()`는 2/3/4만 보므로 충돌하지 않는다"는 틀렸다. 지금 코드는 2·8·11을 warn, 3·9·12를 charge, 4·10·13을 stun으로 본다. 신규 14~번 코드를 매핑하지 않으면 **예고 몸 포즈 채널 (a)가 통째로 평시 보행으로 렌더된다**(E34의 1800프레임 중 702프레임 사고와 같다).
5. **`bodyVisible` 조건과 `TYPE_NAMES` 확장**: 지금은 `(1..8)|13|14|15|16|POSED_TYPE_INDEX>0`만 몸을 그린다. typeCode 49~63(그리고 E59 미니)이 빠지면 몸이 보이지 않는다.
6. 새 포즈 클래스: 매복 웅크림(E58), 와인드업(E55), 잠복(E60), 무리 지휘(E51)가 필요하다. `buildPosedZombieStatePose`에 상태를 추가한다.
7. 소품 최소 두께: 로컬 **0.06 이상**. 월드 0.02u ≈ 1.2 CSS px이고, 이보다 얇으면 아웃라인도 보이지 않는다.

### 4.3 서로 너무 비슷한 얼굴 (해상도 11×7 CSS px에서 형태 차이가 사라지는 쌍)

1. **E46 · E48 · E55, 비대칭 눈 3종**: "한쪽은 크게 뜬 원, 한쪽은 작거나 감은 눈"이 세 번 나온다. 특히 E48(윙크 + 분홍 혀)과 E55(조준 감은 눈 + 분홍 껌)는 아래쪽 분홍 요소까지 같아서 거의 구별되지 않는다.
   - `[권고]` 비대칭 눈은 **E46만** 쓴다.
   - E55는 **챙 그림자 띠 + 그 안에서 빛나는 작은 두 눈 + 분홍 껌**으로 바꾼다(모자 실루엣과 일치).
   - E48은 **겨자색 자 띠(이마를 가로지르는 두꺼운 밝은 띠) + 둥근 양눈 + 혀**로 바꾼다.
2. **E47 · E51, 닫힌 곡선 눈 + 둥근 입**: ∩ 눈과 초승달 눈은 1px 차이밖에 나지 않는다. 남는 차이는 입 크기뿐이다.
   - `[권고]` E47은 **분홍 홍조 면적을 키워 주 식별 요소로** 삼는다(볼 원 반경 0.08 이상).
   - E51은 **세로 O 입을 얼굴 높이의 35% 이상**으로 키우고 입 안을 와인색으로 칠한다.
3. **E52 · E57, 렌즈형 눈 링**: 장치 5px 크기에서 원형 링과 사각 링은 같아 보인다.
   - `[권고]` E52는 **렌즈를 늘 반투명 연두로 채운다**(텔레그래프에서는 밝기만 올린다). 그을음 영역도 유지한다.
   - E57은 **검은 굵은 테 + 흰 반사**로 무채색을 유지해 색으로 갈라 준다.
4. 참고: E56(처진 눈)은 흰 마스크, E58(> <)은 살구색 반창고가 큰 색 영역이라서 같은 "닫힌 눈" 계열이어도 구별된다. E59(세로 점 눈)와 E53(세로 타원 눈)은 흰 우유 콧수염과 이색 눈으로 구별된다. E60의 노란 발광 눈은 E07의 크림색 눈과 비슷하지만, 등장 스테이지가 다르고(E07은 Stage 2, E60은 Stage 4) 수면선이 있어서 허용한다.

### 4.4 색 원칙

- 눈 색 기본값이 기존 박스 눈 좀비(빨강 발광 eye 박스, emissive 0.9)와 겹치지 않게 15종 눈 색을 팔레트 표로 먼저 확정한다.
- 텔레그래프 색(빨강 점멸)은 E54 하나에만 쓰지 말고 **"공격 임박 = 눈이 경고색"을 공통 문법**으로 쓰는 편이 작은 화면에서 학습하기 쉽다. 종별 고유 연출은 그 위에 더한다. 이 부분은 uimini와 balanceqa에 넘길 판단 사항이다.

## 5. §2~§4에 대한 그 밖의 지적

- **정책 선행 조건**: `project_develop_policy.md` Graphic Designer 부서 정책에 따라 15종은 **2D 콘셉트 시트를 먼저 확정**해야 한다(`Graphic_designer/`). `Graphic_designer/Bang_survivor_Graphic_concept.md`도 참조해야 한다. 이 설계 문서는 텍스트 사양이므로 3D 구현 전에 이 단계를 넣는다.
- **Studio 연결**: 신규 15종은 E34~E45처럼 Studio 대상 typeCode(`STUDIO_TUNED_TYPE_CODES`, `getStudioZombieItemId`)에 등록해야 한다. 그 절차는 `ZOMBIE_E01_STUDIO_TRANSFORM_CONNECTION_CODE.md`를 따른다. 얼굴 쿼드는 E07처럼 **studioNonTunable**로 두고, Studio 파트 키를 새로 만들지 않는다.
  - Studio와 프리뷰(공유 박스 트리 `ZombieMesh`)에서도 **같은 셰이더 모듈을 uniform faceId로** 그려야 Studio=게임 얼굴이 같아진다.
  - 등록에 `GraphicsStudio.jsx` 수정이 필요하면 threemini는 그 파일을 수정할 수 없다(절대 금지). Advisor가 따로 라우팅해야 한다.
- **§1.4 텔레그래프**: 얼굴 채널은 절반의 좀비에만 보인다(§2 Q5). 회피 가능성 자동 테스트는 얼굴 없이 성립해야 한다.
- **§4.2 per-instance 갱신**: `aState`, `aMisc`는 CPU에서 매 프레임 계산한다. `pool.state` 코드 대역(14~)과 상태 타이머의 정본이 `projectileZombieBehavior.js` 한 곳에 있어야 얼굴, 포즈, 데칼이 같은 진행도를 쓴다. 그래서 상태 진행도 계산 함수도 그 모듈에서 export하기를 권한다.
- **E49와 E53 감속 표시**: 플레이어 감속 상태의 3D 피드백(발밑 물결 등)이 문서에 없다. uimini와 threemini가 함께 정해야 할 항목이다.
- **E54와 E58 플레이어 변위**: 넉백과 끌림은 플레이어 3D 모델 좌표가 실제 좌표와 분리되면 안 된다는 정책(주인공 좌표 일치)에 걸린다. 변위는 반드시 플레이어 정본 좌표에 적용하고, 비주얼만 따로 보간하지 않는다.

## 7. 필수 변경 요약 (상위 5개)

1. 얼굴 크기를 **11×7 CSS px / 16×11 장치 px**(DPR 상한 1.5, 45° 원근 축소)로 다시 잡는다. 얼굴형 머리를 ×1.25로 키우고, 얼굴 어휘를 "눈 쌍 + 입 + 큰 색 영역"으로 줄이고, `fwidth` AA와 최소 획 클램프를 쓰고, 겹치는 3쌍(E46/E48/E55, E47/E51, E52/E57)을 색과 면적으로 가른다.
2. 얼굴 InstancedMesh는 `ZombieInstanceLayer` 머리 행렬 체인(box 스케일 직전)에서 쓴다. 용량 200, vec4 `aFace`, **소프트 알파(alphaTest 아님)**, `depthWrite false`, polygonOffset, renderOrder 0.5, eye 슬롯 끄기, 챔퍼 평탄부 안에 둔다.
3. 프리웜: `compileAsync`는 보이는 객체만 컴파일하므로 신규 인스턴스 메시는 **visible 상시 true + count 0**으로 두고, `gl.info.programs`로 검증한다.
4. 몸통과 소품: POSED는 박스 전용이고 소품을 금지하는 구조다. 박스 소품 슬롯 K=3, 양쪽 경로의 로컬 회전(패리티 테스트), 형태 클래스 3종을 추가하고, 1px 미만 소품(헤드셋, 청진기, 물감 점, 줄 체인, 고글 지오메트리, 종이 평판)을 뺀다. `phase()` 14~ 매핑, `bodyVisible`과 `TYPE_NAMES`를 확장한다.
5. E07은 옮기지 않는다(Studio 절대법칙, Apply 유실 위험). 신규 얼굴은 Studio와 프리뷰에서도 같은 셰이더 모듈(uniform faceId)로 그린다. 2D 콘셉트 시트가 먼저다. 투사체는 별도 `NovelProjectileLayer` 형태 클래스(6 드로콜) + SDF 예고 데칼 1개로 만든다.
