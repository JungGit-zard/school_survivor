## 0. 왜 이 표만 고치면 되는가

런타임 좀비 스폰 경로는 **버스트 표 / 마틸다 / 오버타임 보강** 3개뿐이다. `Enemies.jsx`의 프레임 루프에
`SCHEDULE_WAVE`는 존재하지 않고, 오버타임은 300초에 시작하는데 스테이지가 240초에 끝나므로 발화하지 않는다.
`getRuntimeBurstEventsForStage()`는 표를 필터 없이 그대로 돌려준다.

따라서 **스테이지 총 HP는 이 버스트 표 하나가 단독 결정한다.** `waveTimelines.js`의 `*_WAVE_PHASES`는
밀도 파생용 분석 데이터이지 스폰 생성기가 아니다 — 그 사실을 새 회귀 테스트 주석에 명시했다.

적용 HP = `Math.round(ENEMY_STATS[type].hp × STAGE_HP_MULTIPLIER[stage])`,
`STAGE_HP_MULTIPLIER = { stage2: 1.2, stage3: 1.44, stage4: 1.728 }` (Enemies.jsx:765).
특수 크루 인원은 `evt.count`가 아니라 상수 7이 정한다(`RUN_ZOMBIE_CREW_SIZE` / `STAGE2_GUARD_CHASE_SIZE`).

### 브리프 수치 1건 정정

브리프는 스2 경비추격 4회를 2,142 HP로 적었지만, 코드대로 계산하면 **크루 1기 = 516 HP**다:
`round(RZT 140×1.2)=168` + `round(RZG 48×1.2)=58` × 6 = 168 + 348 = 516 → 4회 = **2,064 HP**.
설계는 실제값 516/2,064를 기준으로 했다. 결론(경비추격이 새 예산의 최대 덩어리)은 그대로다.

### 편성 판단 근거

예산이 62% 줄어드는 스테이지라 "무엇을 남기느냐"가 전부였다.

1. **경비추격 4회 → 2회.** 시그니처를 없애면 스테이지 정체성이 사라지고, 4회를 유지하면 2,064 HP =
   새 예산의 60%를 크루 하나가 먹어 나머지 12개 앵커가 굶는다. 그래서 **도입(0:40) + 보스 구간 재현(2:24)**
   2회로 리듬만 남겼다. 1,032 HP = 예산의 30%로, 여전히 스테이지 최대 단일 덩어리다.
2. **혼합 보강 4×17 → 경량 2회.** 옛 풀에는 E02/E04/E05/E06이 섞여 있었는데,
   `pickMixedReinforcementTypes`가 풀의 각 타입을 1마리씩 **먼저 보장**하므로 이건 "랜덤 구성"이 아니라
   **확정 난이도 상승**이었다. 감축분 중 가장 정당한 대상이라 여기서 가장 많이 뺐고, 남긴 2건은
   풀을 `LIGHT_MOB_MIX(E01/E03)`로 제한해 원래 목적(후반 템포 유지)만 남겼다.
3. **마릿수는 오히려 스1 수준으로 맞췄다.** 예산만 보고 자르면 95 → 60마리대로 떨어져 "복도가 텅 빈다"가 된다.
   그래서 뺀 예산의 일부를 경량 물량(E01/E03/E07)으로 되돌려 **95마리 vs 스1 92마리**로 나란히 놓았다.
   HP는 낮고 마릿수는 같다 = 스1보다 부드럽지만 밀도는 유지되는 곡선이다.
4. **도입 사슬 유지.** E03 0:24 → E04 1:12(발사 게이트 `e04IntroSec` 72와 동시각) → E05 2:00 → E06 2:48.
   E04 스폰이 게이트보다 늦어지지 않는지 확인했다(같은 초라 게이트가 먼저 열려 있다).
5. **E04 216초 1마리 제거.** 스2 E04는 이제 72초 1건뿐이다. 스4의 원거리 시그니처와 역할이 겹치지 않도록
   스2에서는 "복도에서 한 번 배우는 타입"으로 축소했다.

### 편성 판단 근거

두 개의 구멍을 같은 예산 증분으로 동시에 메웠다.

1. **빈 앵커 144/150/168/216을 채웠다.** 가장 심한 문제는 2:00~3:04의 **64초 보스 단독 공백**이었다.
   이제 2:24·2:30·2:48에 원거리 벽이 연속으로 들어가 보스전이 "1대1 사격장"이 아니라
   "탄막 속에서 보스를 상대하는 구간"이 된다.
2. **증분은 전부 시그니처 E04에 넣었다: 1마리 → 26마리(전체 71마리의 37%).**
   시그니처가 "원거리 안전지대 소멸"인데 스테이지 전체에 E04가 1마리뿐이던 것이 진짜 결함이었다.
   예산이 +45% 늘었으므로 **마릿수 인플레가 아니라 타입 비중 전환**으로 시그니처를 실현했다
   (스4 설계 원칙 "마릿수로 어렵게 하지 않음"과 일치).
3. **26마리가 26발이 아니다.** 동시 발사는 `getE04Cap('stage4')`(60초 전 2기·이후 3기)과
   `STAGE2_E04_MAX_PROJECTILES = 6`이 하드캡한다. 늘어나는 것은 탄량이 아니라
   **"사선이 항상 살아 있다"는 지속 압박**이다. 또 `Enemies.jsx`의 `bossPressure`는
   `currentStageId !== 'stage4'` 조건이라 **스4는 보스전에도 E04가 계속 쏜다** —
   안전지대 소멸이 보스 구간까지 유지되는 것이 설계대로 작동한다.
4. **2:48은 `ring` E04×9.** 원거리로 플레이어를 완전히 포위하는 형태 = 시그니처를 문자 그대로 구현한
   유일한 버스트다. 예고 라벨을 "사방에서 급식판이 날아온다"로 새로 넣었다(예고 5건, 배열 순서 `60 → 108 → 120 → 168 → 184`).
5. **2:30에 E03×6을 함께 넣은 이유.** 원거리만 깔면 플레이어가 벽 뒤로 붙어 사선을 죽인다.
   러너를 섞어 자리에서 밀어내야 원거리가 실제로 기능한다 — 두 타입이 서로를 살리는 조합이다.
6. **216초 차저 러시 추가.** 스1·스3의 "마틸다 직전 E05 러시" 관용구를 스4에도 채용해
   마틸다 등장 직전 리듬을 네 스테이지에서 통일했다.
7. **RZL 미채용 / 형태는 `ring`·`pincer`만.** 기존 원칙 유지(RZL은 스3 전용 시그니처).

## 5. 부수 영향

- **`ALL_STAGES_110SEC_SMILING_TANKER_REINFORCEMENT_EVENTS`(스2·3·4 공유 배열)는 분리하지 않았다.**
  세 스테이지가 모두 이 1건을 그대로 쓰는 편성으로 수렴했기 때문이다. 대신 스2가 따로 얹고 있던
  **중복 `{110, E02, 3}`을 제거**해서 이제 세 스테이지가 정확히 1건씩만 갖는다 —
  회귀 테스트도 `toHaveLength(1)`로 통일했다(전에는 스2만 2였다).
- **`STAGE_DENSITY_MULTIPLIER`가 움직였다** (스2 0.641 → 0.921 / 스3 1.055 → 1.110 / 스4 1.316 → 1.221).
  밀도 솔버가 `웨이브 base × m² + 버스트 잡몹 base × m + 크루 확정 HP = 앵커 × factor`를 풀어 m을 내므로,
  버스트 잡몹 base가 줄면 같은 factor를 맞추려 웨이브 몫이 커진다.
  **게임플레이 영향은 없다** — 랜덤 웨이브는 런타임에 발화하지 않는다. 다만 언젠가 웨이브를 되살리면
  이 값이 즉시 스폰량으로 나타나므로, 테스트에 그 사실을 주석으로 못박았다.
- **어드민 미러 행 수**를 리터럴 29에서 `STAGE2_BURST_EVENTS.length` 파생으로 바꿨다(현재 19).
  스폰 표가 정본이므로 표 길이에서 파생하는 것이 옳다.

### 이 작업 범위 밖의 기존 결함 1건 (uimini 후속)

`STAGE2_SPAWN_TELEGRAPHS`는 빈 배열이고 주석은 "stage2 형태 버스트는 런타임 발화를 중단했다"고 적혀 있는데,
**현재 `getRuntimeBurstEventsForStage`는 필터 없이 표 전체를 돌려주므로 스2 형태 버스트도 실제로 발화한다.**
즉 스2만 `swarm`(0:40)·`ring`(1:00)·`pincer`(2:30) 세 형태가 **예고 없이** 들어온다.
이번 재설계로 생긴 문제는 아니지만(이전에도 네 형태가 예고 없이 발화했다) 스3·스4는 예고가 있고 스2만 없다.
스2 예고 3건 추가 + HUD 배선은 uimini 범위라 여기서는 손대지 않고 기록만 남긴다.

| 총 HP ±2% (스테이지 4종) | `round(3710 × 1.3^n)` 목표 대비 오차 ≤ 2% |
| 실측 총 HP 사다리 | `[3710, 4838, 6308, 8166]` + 단계 비율 1.27~1.33 + **스1 = 3710 고정** |
| 앵커 부분집합 (스테이지 4종) | 보스 제외 모든 sec ∈ 13개 앵커 |
| 앵커 전수 사용 | 네 스테이지 모두 13개 앵커를 빠짐없이 씀(긴 공백 금지) |
| 보스 시각 불변 | 150 / 120 / 135 / 140 |
| 동시 상한 | 한 앵커 최대 스폰 ≤ 150 |

목표값을 리터럴이 아니라 `STAGE1_TOTAL_HP × 1.3^n`으로 계산하게 해서, 스1이 바뀌면
사다리 전체가 함께 감시되도록 했다.

## 8. R4 — 마틸다 이후 무한모드 스폰안 (설계안, **미구현**)

> 이 절은 설계만이다. 코드는 한 줄도 넣지 않았다. 스테이지 종료 조건 자체가 바뀌는 변경이라
> 사용자 확인이 필요하다.

### 8-0. 먼저 짚어야 하는 전제 충돌

마틸다 스폰은 스1 180초, 스2~4 **230초**(`stageConfig.js`)이고 스테이지는 240초에 끝난다.
즉 **현재 규칙에서는 스2~4에 "마틸다 이후"가 10초밖에 없다.** 무한 곡선은 종료 조건이 바뀌지 않으면
사실상 발화하지 않는다. 그래서 이 설계는 다음 중 하나를 전제로 한다:

- (권장) `endless: true` 모드 플래그 → `durationSec = Infinity`, `escapePortalSec = null`(포탈 미개방).
  기존 4스테이지 클리어 규칙은 그대로 두고 별도 모드로 분리한다.
- (대안) 탈출 실패 시에만 무한 연장. 이 경우 스1(마틸다 180 / 포탈 210 → 30초)만 의미가 있다.

또한 현재 오버타임 코드(`OVERTIME_REINFORCEMENT_START_SEC = 300` / 30초 간격 / 30마리)는
**한 번도 발화하지 않는 죽은 코드**다. 아래 설계는 이 상수 3개를 마틸다 상대 시각 기반으로 교체하는 것이다.

### 8-1. 설계 원점: 좀비의 역할이 바뀐다

마틸다는 **접촉 즉사**다. 그러므로 마틸다 등장 이후 좀비의 목적은 "플레이어에게 피해를 주는 것"이 아니라
**플레이어의 발을 묶어 마틸다에게 잡히게 하는 것**이다. 이 한 문장이 아래 모든 수식의 근거다.

세 가지 귀결:

1. **좀비는 지형이 되어야 한다.** 처치 가능한 좀비는 벽이 아니다 → HP를 시간에 따라 올린다.
2. **막는 타입이 우선, 원거리는 최후.** E04는 거리를 벌리고 서 있어서 길을 막지 못한다 —
   일찍 넣으면 오버타임이 오히려 *쉬워진다*(잡기 좋은 표적이 늘어남).
3. **스폰 위치가 마릿수보다 중요하다.** 플레이어와 마틸다 **사이**에 스폰된 좀비는 공짜 XP다.
   플레이어의 **도주 방향**에 스폰된 좀비만 벽이 된다.

### 8-2. 수식

`T0 = stageConfig.matildaSec` (스1 180 / 스2~4 230), `τ = elapsedSec − T0`, 웨이브 번호 `n = 1, 2, 3, …`

**웨이브 간격 (점진 단축, 하한 있음)**

```
I(n) = max(6, 20 − 2×(n−1))            [초]
     → 20, 18, 16, 14, 12, 10, 8, 6, 6, 6, …
τ_n  = Σ(k=1..n−1) I(k)
     → 0, 20, 38, 54, 68, 80, 90, 98, 104, 110, 116, … (이후 +6 고정)
```

n=1은 τ=0, 즉 마틸다 등장과 동시에 발화한다. 초반 20초 간격은 "마틸다는 못 죽인다"를 플레이어가
학습할 여유를 주기 위한 것이고, τ≈90(약 1분 30초 뒤)부터 6초 드럼비트로 고정된다.

**웨이브 마릿수 (선형 증가, 동시 상한이 실질 캡)**

```
C(n)    = min(40, 8 + 4×(n−1))
        → 8, 12, 16, 20, 24, 28, 32, 36, 40, 40, …
실제 스폰 = clampZombieSpawnRequest(C(n), totalZombieCounts(), MAX_CONCURRENT_ZOMBIES)
```

`clampZombieSpawnRequest`는 이미 존재하는 함수이므로 새 코드가 필요 없다.
필드가 150에 도달하면 웨이브는 자동으로 **"150 유지 보충"** 으로 성격이 바뀐다 — 이것이 의도된 종착 상태다.

**HP 증가식 (좀비를 지형으로 만드는 레버)**

```
overtimeHpMultiplier(τ, stageId) = STAGE_HP_MULTIPLIER[stageId] × (1 + 0.06 × floor(τ / 15))
```

15초마다 +6%. τ=60 → ×1.24, τ=120 → ×1.48, τ=300 → ×2.2, τ=600 → ×3.4.
**기하급수가 아니라 τ에 선형**으로 잡은 이유: 목표는 "못 치운다"이지 "못 깎는다"가 아니다.
지수 증가는 몇 분 뒤 단일 개체가 수만 HP가 되어 피드백(피격 반응·처치 연출)이 죽는다.

**타입 도입 순서 (역할 기반 — 막는 놈 먼저, 못 막는 놈 마지막)**

| 웨이브 | 추가되는 타입 | 근거 |
|---|---|---|
| 1–2 | E01, E07 | 몸으로 길을 메우는 기본 잡몹. 마틸다 등장 순간의 가독성을 지키려 경량만 |
| 3–4 | + E02 | 탱커 = 실질적 벽. 처치 시간이 길어 통로를 오래 점유한다 |
| 5–6 | + E03 | 러너 = 카이팅 차단. 도주 경로를 먼저 끊는 역할 |
| 7–8 | + E06 | 거대 = 이동 가능 지형. 1마리가 통로 하나를 지운다 |
| 9+ | + E05 | 차저 = 밀어내는 압박. 마틸다 쪽으로 되밀기 |
| 13+ | + E04 (**스4만 1부터**) | 원거리는 못 막으므로 최후. 스4는 시그니처라 예외 |

**스폰 위치 (설계의 핵심)**

플레이어에서 마틸다를 향한 반대 방향, 즉 `dir = normalize(playerPos − matildaPos)`를 중심으로 한 호에 스폰한다.

```
arcHalfAngle(n) = max(75°, 120° − 5°×(n−1))     // 도주 방향으로 점점 좁혀 조인다
R(n)            = max(4.5, 6.5 − 0.25×(n−1))    // 반경도 좁혀 반응 시간을 줄인다
```

기존 `randomSpawnPos` + `getStageObjectSightObstacles(stageId)` 제약(장애물·경계·최소 반경)은 그대로 준수한다.

**타입별 동시 상한 (필드가 거대 떼로 균질해지는 것 방지)**

```
E06 ≤ 6 동시,  E02 ≤ 30 동시,  E04 = getE04Cap(그대로),  나머지 무제한(총 150 이내)
```

### 8-3. 배선 제안 (구현 시)

## 10-2. 결함 1 — 스3 사다리 위반 (+8.98%)

`STAGE3_25_SECOND_GREEN_SMILING_REINFORCEMENT_EVENTS`는 25초 간격 · 150초 미만이라

### 삭제하지 않고 상쇄한 이유

이 반복 보강은 사용자가 별도로 지시한 기능이다. 그래서 **기능은 그대로 두고 같은 창에서만 예산을 뺐다.**
반복이 넣는 525 HP는 전부 25~125초 창에 있으므로, 그 창 밖을 건드리면 스테이지의 긴장 곡선이 바뀐다.

### 감축 내역 (-562 HP)

| 시각 | 변경 | HP | 근거 |
|---|---|---|---|
| 110s | `E06 ×1` **삭제** | −461 | 목적이 "거대 조기 등장 보장"이었는데, 그 창을 이제 반복 보강이 25초마다 채운다. 역할 중복. |
| 72s | `E05 2 → 1` | −101 | 반복 tick 75초가 바로 옆에 붙는다. "차저 첫 등장 신호"는 ×1로 충분(스1 E06·스4 E06도 ×1 도입). |

창 순변화 = +525 − 562 = **−37**로 사실상 중립. 스테이지 총합만 사다리로 돌아온다.

**건드리지 않은 것**: 시그니처 RZL 크루 4회(370 × 4 = 1,480), 216초 차저 러시,
`ALL_STAGES_110SEC_*`(스2·3·4 공유 배열), 보스 150초, 마틸다 210초.

### 거대(E06) 배치가 184초 한 곳이 된 이유

대안은 184초 `pincer E06×2`를 ×1로 줄이고 110초를 남기는 것이었다. 그건 안 된다 —
**pincer는 앞뒤 두 방향이 성립 조건**이라 ×1이면 형태 버스트의 의미가 사라진다.
따라서 스3 거대는 184초 앞뒤 벽 하나로 모았다. 플레이어는 스1·스2에서 이미 168초에 E06을 만난다.

- 반복 보강은 **별도 describe로 직접 검증**한다: stage3 전용일 것, 전개 시각이 `[25,50,75,100,125]`일 것,
  마지막 tick이 보스 등장(150)보다 앞설 것, 풀이 경량대(E01/E07)일 것.
- **총 HP 단언에서는 예외가 없다.** `stageTotalHp`가 tick 수만큼 전개해 전량을 센다.

## 10-4. 결함 2 — 스4 E04 포화점 계산

### 옛 근거가 틀렸다

옛 주석은 "동시 발사는 `getE04Cap`(stage4: 60s 전 2기·이후 3기)이 하드캡한다"를 근거로 E04를 26마리까지
올렸다. **`getE04Cap`은 런타임 호출자가 없는 죽은 코드다** (`grep -rn "getE04Cap" src` → 정의 + 주석뿐).
사수 수를 제한하는 장치는 게임 어디에도 없다.

### 실제 상한 = 투사체 슬롯 회전율

유일한 게이트는 `enemySimulation.js:294` `projectileCount < E04_MAX_PROJECTILES(6)` —
**사수 수가 아니라 비행 중 투사체 6발** 상한이다. 투사체는 플레이어에게 명중하거나
수명 3,200ms가 다 차야만 슬롯을 반납한다(`enemyProjectilePool.js`, 경계 despawn 없음).

```
처리량 천장  = 6발 / 3.2s                 = 1.875 발/초
사수 1기     = 1 / 2.2s (rangedCooldown)  = 0.4545 발/초
포화 사수 수 = 1.875 / 0.4545             = 4.13기
```

- 4기면 이미 천장의 **97%**다. 5기째부터는 슬롯 대기열만 길어지고 화면 압박은 그대로다.
- 초과분은 접촉 위협도 못 준다: E04는 `preferDist 5.5`에서 스트레이핑만 하고
  `minDist 3.5` 안으로는 오히려 후퇴한다(`resolveRangedEnemyVelocityRaw`). = 순수 HP 낭비.
- 보스 구간은 더 낮다. B04가 같은 pool을 2,600ms로 쓰므로 3.2/2.6 = **1.23슬롯**을 상시 점유 →
  E04 포화점 **3.3기**.

옛 26마리 중 144/150/168초의 23마리는 24초 안에 쏟아졌다 — 포화점의 5배 이상, 약 1,000 HP 낭비.

### 개정 편성 — "등장당 정확히 4마리"

| 시각 | 변경 | HP |
|---|---|---|
| 24s | `E04 3 → 4` | +55 |
| 144s | `E04 8 → 4` | −220 |
| 150s | `E04 ×6` **삭제** | −330 |
| 168s | `E04 ×9 ring → ×4 ring` | −275 |

E04 총 26 → **12마리**(회수 770 HP). 규칙이 자기설명적이다: 등장마다 `floor(4.13) = 4`.

**시그니처는 유지된다.** 스4는 `bossPressure` 예외라(`Enemies.jsx:1617`, `Enemy.jsx:973`이 stage4를 면제)
보스전에도 E04가 계속 쏘는 **유일한** 스테이지다. 144·168 두 벽이 보스 구간(150~)을 앞뒤로 감싼다.
`STAGE4_SPAWN_TELEGRAPHS`의 168초 "사방에서 급식판이 날아온다"는 4기로도 그대로 성립한다.

### 회수한 770 HP → 근접 압박으로

E04가 못 하는 일이 거리 좁히기다. 좁은 급식실(halfX 14.4 / halfZ 16)에서 카이팅을 끊는 건 근접 편성뿐이다.

| 시각 | 추가 | HP | 의도 |
|---|---|---|---|
| 108s | `E07 ×2` | +56 | 탱커 협공 옆 경량 속공 |
| 144s | `E02 ×2` | +242 | 원거리 벽 아래 탱커 몸통 |
| 150s | `E05 ×3` | +363 | 보스 등장 동시 차저 (옛 E04×6 자리) |
| 168s | `E07 ×4` | +112 | 원거리 포위 안쪽을 메우는 속공 |

합계 +773. 순변화 +3 → 잡몹 5,574 → 5,577.
**스4 정체성 유지**: ring/pincer만(swarm/gauntlet 배제), RZL 미채용, 형태 버스트 5개·시각·배열 순서 불변

## 10-5. 테스트 면제 제거 경위

제거 전 `burstEvents.test.js`의 총 HP 단언은 이랬다:

```js
const stageTotalHp = (stageId) => getRuntimeBurstEventsForStage(stageId)
  .filter((event) => stageId !== 'stage3' || event.reinforcement !== 'stage3TwentyFiveSecondE01E07')
```

**사다리를 지키라고 만든 단언이 위반 항목만 골라 빼고 초록이었다.** 실측 6,833(+8.98%)인데
테스트는 6,308을 세고 통과했다. `stage3BaseEvents` 헬퍼도 같은 면제를 앵커 단언에 적용하고 있었다.

개정:

1. `stageTotalHp`의 필터를 **삭제**하고, `isRepeatingBurstEvent` / `repeatingBurstTickCount`로
   tick 전개분까지 전부 세는 `eventTotalHp`를 넣었다.
2. `stage3BaseEvents`(특정 reinforcement 이름 기반) → `singleShotEvents`(구조 기반, `!isRepeatingBurstEvent`).
   특정 이벤트를 이름으로 봐주는 게 아니라 "반복형은 앵커 규칙 대상이 아니다"라는 규칙을 표현한다.
3. 새 단언 2건 추가: 반복 보강 규칙(stage3 전용 · 전개 시각 · 보스 이전 종료 · 경량 풀),
   반복 전개 총량 못박기(30마리 / 525 HP / 스3 총 6,271).
4. 새 단언 1건 추가(결함 2 감시): E04 포화점을 상수에서 계산해 `4.125`를 확인하고,
   스4 E04가 24/144/168 세 앵커에 각 4마리 · 총 12마리인지, 다른 스테이지로 번지지 않았는지 본다.

acceptance 기준:
