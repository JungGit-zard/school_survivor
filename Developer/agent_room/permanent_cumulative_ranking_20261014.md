# 무제한 누적 랭킹 영구 보드

- Kanban: `backendmini` / `t_75f70424`.
- 기존 일일·주간 보드의 엔트리 구조와 경로를 보존하고 두 영구 제출 버킷을 추가한다.
- 영구 경로는 `rankingService/v1/public/all-time/global/allTime/all-time/entries/{uid}` 및 `.../stage/{stageId}/allTime/all-time/entries/{uid}`다. 날짜·주·시즌이 바뀌거나 시즌이 닫혀도 동일한 최고점 기록을 읽고 저장한다.
- 글로벌은 이전 스테이지까지 합산된 연속 런 `score/globalTimeMs`, 스테이지별은 그 판의 `stageScore/timeMs`를 기록한다. 점수 상한을 추가하지 않았다.
- 최초 0점도 본인 엔트리를 만든다. 이미 존재하는 더 높은 최고점은 새 0점이나 낮은 점수로 덮지 않는다. 게임 진입 시 등록과 게스트 이름 입력 호출은 별도 UI 작업에서 연결한다.
- 게스트는 별도 Firebase anonymous Auth 클라이언트를 전달받아 본인의 인증 UID로만 기록한다. 메인 Google 로그인과 개인 진행도 저장을 변경하지 않는다. 익명 유저 표시명은 본인이 입력한 `user.displayName`을 사용한다.
- 규칙은 기존 본인 UID·최고점·필드 타입·스테이지 허용목록을 유지한다. `allTime`은 시즌 및 기간이 모두 `all-time`인 경로에만 허용하며 비인증 쓰기를 허용하지 않는다.
- `allTime` 조회·구독에는 시즌 종료 차단과 날짜 경계 재구독 타이머가 없다. 계정 삭제에 영구 글로벌 1개·스테이지 4개를 추가해 현재 삭제 경로는 15개다. 과거 일일/주간 열거 제한은 기존과 동일하다.
- 과거 기록을 소급 변환하거나 만들어 넣지 않았다. 실제 Firebase 데이터를 테스트로 쓰지 않았다.
- 계정 삭제 시 stage 엔트리의 `newData`가 null이므로 stageId 일치 검사는 존재하는 새 엔트리에만 적용한다. 삭제에서도 본인 UID·인증·허용 stage/window 경계는 유지한다. 실제 규칙 표현식으로 본인 null 삭제 허용 및 타인·비인증 삭제 거부를 검사했다.
- 게스트 닉네임 정본은 비공개 `rankingService/v1/guestProfiles/{uid}/nickname`이며 본인 인증 UID만 읽고 쓸 수 있다(문자열 2~12글자, 다른 키 금지). `renameRankingEntriesForUser()`는 알려진 현재·영구 15경로 중 존재하는 본인 엔트리의 `displayName`만 `update`한다. 0점·높은 점수·시간·클리어 상태를 보존하고 없던 스테이지 기록을 생성하지 않는다. 반환은 `{attempted,updated,failed,reason?}`이며 실패를 호출자가 확인할 수 있다. Google 계정 기록 이동은 구현하지 않았다.
- 게스트 제출과 닉네임 갱신은 동일 UID의 Promise 큐에서 순서대로 실행한다. 뒤늦은 제출이 이름 갱신을 덮지 않으며, 큐에서 실제 제출을 시작할 때 UID와 일치하는 Firebase 저장 확인 닉네임을 읽어 과거 user 객체의 이름을 대체한다. 완료된 큐는 정리하고 실패 후 다음 작업도 진행한다. 지연된 쓰기→이름 갱신→옛 user 객체로 새 제출과 실패 후 재시도 두 focused 검사를 통과했다.
- 검증: 메모리 클라이언트로 0점 최초 등록/최고점 보존, 게스트 클라이언트·닉네임, 큰 점수와 일·주·시즌 전환, 시즌 종료 시 영구 저장, 영구 조회·구독 타이머 없음, 삭제 경로를 검사했다. 실제 배포 규칙 표현식으로 본인·비인증·타인·낮은 점수·잘못된 시즌/기간·스테이지를 검사했다. 실제 Auth/Firebase 운영 검증과 규칙 배포는 Advisor 담당이다.
