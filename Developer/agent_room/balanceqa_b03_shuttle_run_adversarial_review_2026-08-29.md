전체 스킬 소요 = 텔레그래프 1250 + 왕복 2526~5053 + 경직 1200 = **4.98~7.52초**.

### 회피 창 — "왕복이 짧아지면 피하기 어려워지는가?" → **아니다. 변하지 않는다.**

- Z 판정 밴드 반폭 0.6, 플레이어 이속 3 u/s → 밴드 이탈에 필요한 시간 = **200 ms**.
- 텔레그래프는 거리와 무관하게 **1250 ms 고정**.
- 최단 케이스(편도 1263 ms)에서도 회피 가용 시간은 최소 1250 ms, 필요 시간의 **6.25배**.
- 결속 제약(binding constraint)은 패스 길이가 아니라 텔레그래프다. 패스가 짧아지면
  "위험지대가 점유되는 시간"이 줄 뿐 **회피 난이도는 전혀 오르내리지 않는다.**

### 비대칭 — "필살기 무력화 수준인가?" → **무력화 아님. 다만 위협도 하락의 주범은 이게 아니다.**

플레이어 이동 한계(`playerMovementBounds.js`, stage3): X [-5.5, +5.5], Z [-15.2, +18.4].
플레이어가 밟을 수 있는 면적 = 11 × 33.6 = 369.6.

| 조건 | 위험 면적 | 플레이어 가용면적 대비 |
|---|---|---|
| 수정 후 최악(보스 x=0) | 5.5 × 1.2 = 6.6 | **1.8%** |
| 수정 후 최선(보스 x=±5.5) | 11 × 1.2 = 13.2 | **3.6%** |
| 수정 전(전폭 스윕) | 11 × 1.2 = 13.2 | 3.6% |

X 비대칭이 깎는 몫은 최악의 경우에도 3.6% → 1.8%다. **절대량이 원래 미미해서
무력화라 부를 수준의 변화가 아니다.** 안전지대 평균 25%, 최악 50%.

**진짜 위협도 하락은 X가 아니라 레인 Z 변경(수정 2)이다.**

- 수정 전: `laneZ = clamp(playerZ)` → 발동 순간 플레이어는 **100% 레인 위**. 반드시 Z로 피해야 했다.
- 수정 후: `laneZ = bossZ` → 레인 위에 있으려면 발동 시점에 `|playerZ - bossZ| < 0.6`.
  보스-플레이어 거리 5유닛·방위각 균등 가정 시 대략 **15% 전후**(추정, 실측 아님).
- 즉 "무조건 회피 행동 필요" → "대부분 아무것도 안 해도 안 맞음"으로 바뀌었다.

단, 수정 전 판정은 **공정하지 않았다.** 보스는 `_vel.z = 0`으로 자기 Z를 달리는데
판정은 플레이어 Z 기준이라, 화면에 보이는 보스 몸통과 무관한 유령 히트박스였다.
따라서 이 변경은 "불공정하게 위협적" → "공정하지만 약함"의 교환이고 방향은 옳다.
그러나 **위협도 회복 여부는 밸런스 결정 사항이므로 levelmini/사용자 승인이 필요하다.**

### 피격 판정 일관성 / 터널링

- 판정: Z는 `state.laneZ`, X는 `shuttleX`(해석적 목표 X, 물리 t.x 아님).
  `laneZ = clamp(bossZ, ±18.2)`이고 보스는 `_vel.z = 0`으로 Z를 유지하므로,
  `|bossZ| <= 18.2`인 한 **경고선 = 보스 실제 주행선 = 판정선**이 정확히 일치한다(D1은 예외).
- X 터널링: 60fps 프레임 이동 0.0871유닛, 판정 창 폭 1.4유닛 → **창 안에 16.1프레임 체류**.
  창을 건너뛰려면 delta > 268 ms(약 3.7fps). **터널링 불가.** 판정에 물리 t.x가 아니라
  shuttleX를 쓰므로 물리 지연에 의한 누락도 없다.

### 무적시간 상호작용 — 주석의 주장은 **대부분 사실이 아니다**

- i-frame = `INV_DURATION = 520` ms(`src/components/Player.jsx:15`), `damagePlayer`는
  `invulnerable`이면 early return(`useGameStore.js:323`). `IGNORE_INVULNERABILITY` 미사용 확인.
- 두 패스 사이 피격 간격 = `2 × |endX - playerX| / 5.225`.
- 520 ms 안에 들어오려면 `|endX - playerX| < 1.3585` 유닛, 즉 **플레이어가 반환점(±6.6)
  코앞 1.36유닛 안에 서 있을 때만** i-frame이 2연타를 거른다.
- 예: 보스 x=0, 플레이어 x=3.0 → 간격 1378 ms ≫ 520 ms → **두 번 다 적중**.
  총 손실 = 1 − 0.7² = **51%**.
- 위치 균등 가정 시 2연타 성립 확률: 수정 전 약 89.7%, 수정 후(보스 x=0) 약 79.4%.
  → 편도 단축이 i-frame 중첩 확률을 오히려 조금 **올려** 치사성을 더 낮춘다.

51% 자체는 확정 사양(0.3 × 2패스)의 산술적 귀결이라 사양 위반은 아니다.
문제는 `Enemy.jsx` B03 피격 블록 주석이 "i-frame이 2연타를 걸러준다"고 단정한 점이다.

## 결함 (심각도 순)

### D1 (중) — 레인 Z clamp와 보스 실제 Z의 불일치가 아레나 Z 끝에서 살아남는다

- 재현 조건: 발동 시점 보스 `|t.z| > 18.8`.
- `getB03ShuttleRunLaneZ`는 laneZ를 ±18.2로 clamp하지만, 보스의 실제 t.z는
  stage3에서 아무것도 clamp하지 않는다 — `writeSpecialEnemyVelocityWithinStageBounds`는
  `Enemy.jsx:1122`에서 **stage4에서만** 호출된다. 넉백은 보스를 플레이어 반대편으로 민다.
- 실측:

  ```
  bossZ 18.6 -> laneZ 18.20  mismatch 0.40  보스가 자기 판정밴드 안: true
  bossZ 19.0 -> laneZ 18.20  mismatch 0.80  보스가 자기 판정밴드 안: false
  ```

- 결과: 보스 몸통이 자기 위험지대 **밖**을 달린다. 보스에 붙어 선 플레이어는 안 맞고,
  1.3유닛 떨어져 보이는 플레이어가 30%를 맞는다 — 이번에 고친 그 버그 유형 그대로다.
- 제안: B03 레인 Z는 clamp하지 말고 보스 Z를 그대로 판정에 쓴다(보스는 이미 아레나 안이다).
  clamp가 필요한 이유는 레인 **메시**의 벽 관통이라는 시각 문제뿐이므로, 판정용 laneZ와
  메시 position을 분리하거나(메시만 clamp) 0.49유닛 관통을 수용한다.

### D2 (중하) — 경고선이 실제 스윕 구간과 불일치(전폭으로 그려짐)

- `B03ShuttleRunVisual`의 `boxGeometry args={[halfX * 2, ...]}`, 위치 x = 0.
  레인은 항상 아레나 **전폭**(±7.5)으로 그려진다.
- 수정 1 이전에는 실제 스윕이 전폭이라 정확했지만, 이제 실제 스윕은 `[startX, endX]`뿐이다.
  보스 x=0이면 그려진 선의 **절반이 거짓 경고**다.
- 방향은 안전한 쪽(과대 경고 → 예고 없는 피격은 발생하지 않음)이라 치명적이지 않다.
- 주의: 이 과대 경고가 비대칭 문제를 플레이어 체감에서 가려주고 있다. **시각만 정직하게
  고치면(스윕 구간만 그리기) 필살기가 "눈에 띄게 절반이 안전한" 기술이 된다.**
  시각 수정과 커버리지 수정은 반드시 함께 판단해야 한다.

### D3 (하) — 주석이 i-frame 보호를 과장

- "i-frame이 2연타를 걸러주는 쪽이 안전하다"는 플레이어가 반환점 1.3585유닛 이내일 때만 참.
  일반 위치에서는 두 번 다 맞아 51% 손실. 잘못된 주석은 다음 수정자를 오도한다.
  실제 임계값을 적어두거나 문장을 정정할 것.

### D4 (하) — `animPhase 'run' → 'normal'`은 시각적으로 무변화(no-op)

- `ZombieMesh.jsx:787` 이하에 `'run'` 분기가 없고 `retreat`(864)/`warn`(898)/`stun`(941)
  어디에도 걸리지 않아 **옛 `'run'`도 이미 맨 아래 기본 걷기 사이클로 떨어졌다.**
  `amp` 계산도 `animPhase === 'charge' ? 0.55 : 0.38`이라 두 값이 동일 결과.
- 이번 "정지자세" 해소는 전적으로 `_applyRotation` 추가(수정 3) 덕분이다.
  결함은 아니지만 커밋 메시지에서 animPhase 변경을 시각 수정 요인으로 적으면 사실과 다르다.
- 잔여 리스크(**미확인, 시각 실측 안 함**): 걷기 사이클 주파수는 `freq = 7.0` 시간 기반
  고정이고 속도 연동이 아니다. 보스는 평소 대비 10배 속도로 달리므로 발 미끄러짐
  (foot sliding)은 남아 있을 가능성이 높다. 실기기/실플레이 확인 필요.

### D5 (하) — 반환 시 180° 회전에 약 133~200 ms 소요, 그 사이 뒤를 보고 달린다

- `_applyRotation` turnRate 0.25 lerp, 잔여각 = π × 0.75^n.
  n=8 → 0.31 rad(18°), n=12 → 0.10 rad(5.7°). 60fps 기준 133~200 ms.
- 최단 패스(1263 ms)의 약 16% 구간. 관성 표현으로도 읽히는 수준. 차단 사유 아님.
- 텔레그래프 1250 ms(75프레임) 동안 미리 돌아서므로 **첫 패스 시작 시점의 방향은 문제없다**(확인).

### D6 (하) — 깜빡임 useFrame이 일시정지를 존중하지 않는다

- `Enemy` 본 시뮬레이션 useFrame은 `phase !== 'playing'`에서 early return(`Enemy.jsx:1108`).
- 새로 추가된 `B03ShuttleRunVisual`의 useFrame(`Enemy.jsx:657`)에는 그 가드가 없다.
  레벨업 카드 선택 등으로 정지한 동안 셔틀 상태는 얼어 있는데 `telegraphMsRef`만 계속 쌓인다.
- cos가 주기함수라 값은 [0.25, 1]에 머물어 크래시·시각 파탄은 없다. 다만 재개 후
  "선이 완전히 밝아지는 순간 = 돌진 시작"이라는 학습 가능한 큐가 어긋난다.
- 제안: 누적 전에 `useGameStore.getState().phase === 'playing'` 확인, 또는 상태의
  `elapsedMs`를 prop으로 내려 그걸로 계산.

## 사용자가 제안한 대안에 대한 판정

- **"3패스로 늘리기" → 확정 사양 위반이므로 채택 불가.** 패스 3회면 최대 손실이
  1 − 0.7³ = **65.7%**로 뛴다. "왕복(2패스) 구조"가 못박힌 사양이므로 이 경로는 막혀 있다.
- **대안 B (권장): 패스 2회를 유지하되 복귀 지점을 출발점이 아니라 반대편 끝으로.**
  pass0 = bossX → 먼 쪽 끝, pass1 = 먼 쪽 끝 → 반대편 끝. 순간이동 없음(출발은 여전히 보스 위치),
  패스 2회 유지, 피해 상한 51% 유지, **X 커버리지 100% 회복**. 총 이동 19.8~26.4유닛 → 3.79~5.05초.
  구현 비용: `passDurationMs`가 현재 단일 값이라 패스별 길이를 갖도록 바꿔야 한다
  (`getB03ShuttleRunX`의 pass1 보간과 `advanceB03ShuttleRun`의 `passIndex` 계산 동반 수정).
- **대안 C (최소): 아무것도 안 바꾸고 D2 시각을 현행 유지.** 전폭 경고선이 비대칭을
  체감상 가려주므로, 위협도 회복이 불필요하다고 판단되면 이 상태로도 플레이는 성립한다.
