### 1.1 ID와 타입 코드

- ID는 **E46~E60**, typeCode는 **49~63**이다. E59 미니(우유갑)는 별도 typeCode 64를 쓴다(2차).
- `lib/expansionPersistence.test.js:79,83`과 `lib/finalBackendCompatibility.test.js:27`이 E46을 "없는 타입" 예시로 쓴다. 등록할 때 예시 ID를 E99로 바꾸고, `database.rules.json`의 encounter 허용 목록을 넓힌다. 규칙 배포는 **origin 기반 트리에서만** 한다(F: 트리 배포 사고 2회 기록이 있다).
- 1차에서도 typeCode는 15종 전체를 예약해 번호가 바뀌지 않게 한다.

### 1.2 HP·XP 대체 원칙과 회계

- host는 **실제로 대체하는 `burstEvents.js` 행**이다. 같은 sec, 단발, 비포메이션, 비공유 행이어야 한다. 신규 종의 hp와 xp는 그 행 타입과 같다.
- 건드리지 않는 것: 포메이션 행(ring, pincer, swarm 등. `waveTimelines` 예고 1:1 계약), `ALL_STAGES_110SEC_*` 공유 배열, `STAGE3_*` 반복 증원 descriptor(2026-08-24 사용자 지시), `STAGE2_MIXED_REINFORCEMENT_EVENTS`.
- **`JARMOB_HP_TYPES`(`Enemies.jsx:827`)에 E46~E60(+미니)을 반드시 넣는다.** 빠지면 보스·크루용 배수를 타서 host와 HP가 갈라진다.
- 실효 HP 주의: count×hp가 불변이어도, 무적·피해 감소·회복이 있으면 실효 HP는 바뀐다. v2는 이 셋을 1차 범위에서 없앴다(E57 감쇄 제거, E60 무적 제거, E56 제외).

### 1.3 Stage 1 제외, Stage 2·3 보스 구간 억제 상속

- Stage 1 이벤트 표에 신규 종 0개(결정 Q1).
- 신규 사수 전원이 기존 보스 구간 원거리 억제를 상속한다. **판정은 런타임 컨텍스트의 `context.bossPressure` 플래그를 그대로 읽는다**(`Enemies.jsx:2015`: stage ≠ stage4 이고 `bossSpawnSec` ≤ sec < `escapePortalSec ?? 210`). 150·210 같은 상수는 쓰지 않는다. 그래야 보스 등장 시각이 바뀌어도 E04와 어긋나지 않는다.
- 플래그가 켜져 있으면 예고에 들어가지 않는다. 이미 시작한 예고는 끝까지 간다(커밋 규칙). 그래서 창 안의 발사는 **창 이전에 진입한 예고만** 허용된다(A10).
- 탈출 구간(`escapePortalSec` 이후 ~240s)에는 E04와 같이 다시 쏜다.
- 잔류형 지대는 따로 앞당겨 막는다. E49는 `bossSpawnSec − 5.6s`(체공 1.6s + 웅덩이 4s)부터 예고에 들어가지 않는다. 보스 등장 시각에 웅덩이가 남지 않게 하기 위해서다.
- Stage 2 신규 사수는 **72~144s 창**에 등장시킨다(E04 첫 발사 72s 이후, 보스 전).

### 1.4 예고(텔레그래프) 규칙

1. **화면 게이트**: 사수 본체가 `screenBounds` 안쪽(각 변에서 0.5u 들어간 영역)에 있을 때만 예고에 들어간다. 매복·착지 같은 트리거도 같은 규칙을 따른다. 착지점이나 착탄점은 화면 안으로 클램프한다.
2. **방향 확정 후 500ms**: 발사 방향이나 착탄점이 **확정된 순간부터 실제 발사까지 최소 500ms**를 둔다. 확정 전 추적 구간은 그 앞에 따로 붙일 수 있다(예: E55 추적 600ms + 확정 500ms).
3. **확정 후 불변**: 확정 뒤에는 방향을 바꾸지 않는다. 예외는 E47 약유도(초당 45°, 누적 90°)뿐이다.
4. **커밋**: 예고가 시작되면 반드시 발사한다. 예고 중 사수가 화면 밖으로 나가도 발사한다(이미 본 예고이기 때문이다). 사수가 예고 중 죽으면 예약을 해제하고 발사하지 않는다(유일한 예외).
5. **채널**: (a) 몸 포즈와 (c) 바닥·공중 데칼이 **필수**다. (b) 얼굴은 보너스 채널이다. 카메라 구도상 어느 순간에나 좀비의 절반만 얼굴을 보이기 때문이다(threemini Q5). 회피 가능성 테스트는 얼굴 채널 없이 통과해야 한다.
6. **공통 경고색 문법**: 예고 중에는 얼굴의 눈이 공통 경고색(§3.1)으로 바뀐다. 종별 고유 연출은 그 위에 더한다.

### 1.5 슬롯 선예약과 상한

- **예고 진입 시점**에 그 공격이 쓸 모든 슬롯(비행, 분열 파편, 바닥 지대)을 all-or-nothing으로 예약한다. 예약에 실패하면 예고에 들어가지 않고, 쿨다운의 25% 뒤에 다시 시도한다.
- 신규 풀 예약 조건: `신규 예약·비행 수 < 스테이지 신규 상한` **그리고** `신규 + 기존 풀 활성 수(E04 + B04 재료) < 스테이지 화면 합계 상한`

| 스테이지 | 신규 비행 상한 | 화면 위 적 투사체 합계(E04·B04 포함) | 신규 바닥 지대 |
|---|---|---|---|

## 3. 절차적 그리기(SDF 프로시저럴 셰이더) 얼굴 스펙 v2

### 3.0 크기와 기준 (threemini 재계산 반영)

- 실제 화면 얼굴은 **약 11×7 CSS px, 장치 16×11px**이다(DPR 상한 1.5, 45° 원근 축소). v1의 "11~12 CSS px, 장치 30px"는 틀렸다.
- 얼굴형 15종은 **머리 박스 자체를 ×1.25**로 키운다(리그 `head.scale`). 그러면 얼굴은 **약 13×9 CSS px, 장치 20×13px**가 되고, 이것이 설계 기준이다. 쿼드만 키우는 방식은 쓰지 않는다(외곽선 밖으로 떠 보인다).
- 이목구비는 머리 앞면 평탄부 안, **UV 0.13~0.87** 범위에 둔다.

| 항목 | 하한 (UV, 머리 ×1.25 기준) |
|---|---|
| 가로 획(두께가 세로 방향) 반폭 | **0.045 이상** |
| 세로 획 반폭 | **0.03 이상** |
| 눈·원 반경 | **세로 0.06 이상, 가로 0.045 이상** |
| 이목구비 간격 | **0.08 이상** |
| 동공 | 색 점으로만 쓰고 식별에는 쓰지 않는다 |
| 얼굴당 요소 | **눈 쌍 1 + 입 1 + 큰 색 영역 1**. 나머지는 장식이며, 장식 없이도 구별되어야 한다 |
| 얼굴당 SDF 프리미티브 | **12개 이하** |
| 예고 변화 | **색 변화 또는 면적 변화만**. 0.03~0.04 동공 이동 같은 미세 변화는 쓰지 않는다 |
| AA | UV 실거리 SDF + `fwidth` AA + 최소 획 클램프 `width = max(width, 0.75 × fwidth(d))` |

### 3.1 공통 경고색 문법

- **예고 중에는 눈 획이나 눈 채움이 공통 경고색 `#FF7A1A`(주황)로 바뀐다.** 기존 박스 눈 좀비의 빨강 발광 눈(emissive 0.9)과 겹치지 않는 색으로 골랐다. 최종 색은 uimini와 balanceqa의 판단이 필요하다(§7).

## 4. 성능과 렌더 구조 v2 (threemini 리뷰 반영)

### 4.1 E07식 개별 메시를 쓸 수 없는 이유 (v1과 같다)

1기당 13 드로콜이다. 40기면 약 520 드로콜이 되어 모바일 예산을 넘는다.

### 4.2 얼굴 InstancedMesh

- **위치**: `ZombieInstanceLayer` 안. head 슬롯(j=0) 행렬을 계산할 때 box 스케일을 곱하기 직전의 행렬을 복사해 얼굴 행렬을 만든다. 순수 함수 `composePooledFaceMatrix(out, headMatrixBeforeBox, headBox, k, eps)`로 만들고 테스트한다. 이렇게 하면 Studio 머리 튜닝, 상태 포즈, 비균등 머리 비례가 자동으로 따라온다.
- 공개 300ms(`SPAWN_REVEAL_MS`), 렌더 티어(NEAR·MID만, FAR 11u 초과는 끔), 피격 플래시, 리셋을 같은 루프에서 공유한다.
- per-instance 값: **vec4 `aFace`(id, phase, state, misc)** 1개 + 필요하면 vec2(종횡비, 플래시). 용량은 **`POOLED_ENEMY_CAPACITY` 200**.
- 재질: **소프트 알파 블렌딩**(`transparent: true, depthWrite: false, depthTest: true`), `polygonOffset`(factor −1, units −4), 머리 로컬 ε 0.006, **renderOrder 0.5**. v1의 alphaTest 권고는 철회한다(작은 이목구비가 크롤링한다).
- 얼굴형 종은 eye 박스 슬롯(1, 2)을 **끈다**. 얼굴 쿼드를 가리기 때문이다.
- 셰이더: 분기 셰이더 1개(1 드로콜). `int(aFace.x + 0.5)`로 `faceN()`을 디스패치한다. three ^0.164.1은 WebGL1을 지원하지 않으므로(WebGL2 전용) highp가 자동으로 붙는다. `uTime`은 `mod`로 감싼다. 저가 기기 첫 컴파일이 150ms를 넘으면 5종씩 묶어 3변형으로 나눈다.
- **프리웜**: `compileAsync`는 `traverseVisible`만 돈다. 그래서 얼굴, 소품, 신규 투사체, 데칼 인스턴스 메시는 **visible 상시 true + count 0**으로 둔다. `gl.info.programs`에 얼굴 프로그램이 있는지를 수락 기준으로 둔다.
- 얼굴은 옆이나 뒤를 볼 때 깊이로 자연스럽게 가린다(빌보드 안 함).

### 4.3 몸통, 소품, 투사체

- v1 정정: "몸통은 기존 배치에 합류, +0~2"는 틀렸다. POSED 13슬롯은 박스 전용이고 소품과 자체 회전을 금지하는 구조다.
- 필요한 기반 확장:
  1. POSED **박스 소품 슬롯 K=3**(+6 드로콜)
  2. 소품 **로컬 회전**: 공유 박스 트리(Studio·프리뷰)와 인스턴스 양쪽에 `T(offset) × R(local) × S(box)`를 넣고 패리티 테스트를 한다
  3. **비박스 형태 클래스 3종**(cylinder8, cone4/8, sphere 저폴리) 공용 풀 약 400(+6)
  4. `phase()` 14~ 매핑, `bodyVisible`과 `TYPE_NAMES`를 49~64로 확장
  5. 새 상태 포즈: 와인드업(E55), 무리 지휘(E51), 매복 웅크림(E58), 잠복(E60)
  6. 소품 로컬 두께 0.06 이상
- 투사체: **`NovelProjectileLayer`** 형태 클래스 box/sphere/cone × 툰 + 외곽선 = **6 드로콜 고정**. 복합 형태는 1발에 인스턴스 2개를 쓴다.
- 예고: 지시선, 점선, 착탄원, 퓨즈원, 조준선, 웅덩이, 음파 띠는 **SDF 예고 데칼 InstancedMesh 1개**로 통합한다(per-instance shapeId). 바닥 데칼 선 폭은 0.06u(약 4 CSS px) 이상이다.

## 5. 난이도 곡선 정합과 포화 재계산

### 5.2 포화 재계산 (1차 6종, 전원 생존 최악)

1차 배치는 모두 단발 1기라서 종별 동시 생존 최대는 1이다(신규 종은 반복 증원·혼합 보강 풀에 들어가지 않는다).

|---|---|---|---|---|---|---|
| Stage 2 | E47 1 = **1** | E04 ≤ 6 (bossPressure 중 0) | ≤ 7 | 신규 8 / 합계 14 | E49 1 (상한 2) | B02 차단선 활성 중 신규 지대 0 |
| Stage 3 | E57 상시 예약 4 = **4** | E04 ≤ 6 (bossPressure 중 0) | ≤ 10 | 신규 12 / 합계 18 | 0 | B03 셔틀런 |
| Stage 4 | E55 1 + E52 4(예약) + E53 3 = **8** | E04 게이트 6 + B04 재료 약 2* | ≤ 16 | 신규 18 / 합계 24 | 0 | **B04 수프 원 최대 16** (예고 1,200ms) |

\* B04 재료탄: 쿨다운 2,600ms, 수명 3,200ms → 비행 약 1.23발(`burstEvents.js` 주석 계산). 상한 자체는 아직 확인하지 못했다. 구현 때 실측하고, 예약 조건(§1.5) 두 번째 항이 합계 24를 강제한다.

- v1 §5의 Stage 4 계산(15종 기준, E60·E56 누락)은 틀렸다. 15종 전부를 v1 상한으로 넣으면 신규만 25발이었다. v2는 1차 6종 기준으로 신규 8발 최악이고, 스테이지 상한과 합계 상한을 모두 지킨다.
- B04 수프: 수프 예고·활성 중에는 신규 지대를 만들지 않는다(1차 Stage 4에는 지대를 쓰는 종이 없다). 감속 디버프를 거는 E53은 수프 예고·활성 중 예고에 들어가지 않는다. 그래서 "감속 상태로 수프 원 탈출 시간이 0.37s → 0.56s로 늘어나는" 연쇄가 생기지 않는다.
- 2차 종을 추가할 때는 이 표를 다시 계산한다. 그래도 스테이지 상한과 슬롯 선예약이 최종 안전장치다.

  - A2 Stage 1 신규 종 0
  - A3 방향 확정 → 발사 ≥ 500ms, 확정 후 방향 불변(E47만 예외)
  - A4 스테이지별 상한 준수(E57 상시 4슬롯 포함), 가짜 예고 0회. 측정 구간은 0~240s(탈출 구간 포함). 측정 도구는 아래 "측정 도구 고정"을 따른다
  - A5 60초 정지 피해 증가 S2 ≤ +10%, S3·S4 ≤ +15%, 카이팅 봇 ≤ +10%. 첫 계측 지점은 Stage 4 40s(E55 + 24s E04×4가 겹친다)
  - A6 60/120/150s 레벨 −1 이내, 210s 수집 XP ≥ 95%. 아래 "측정 도구 고정"을 따른다
  - A7 종별 단독, 얼굴 채널 없이 판정한다
    - 피해형(E47, E52, E55, E57): 회피 봇 피해 0, 정지 봇 피해 > 0
    - **E49(피해 0)**: 정지 봇 **감속된 프레임 > 0**, 회피 봇 **감속된 프레임 0**
    - **E53(피해 + 감속)**: 정지 봇 피해 > 0 **그리고** 감속된 프레임 > 0, 회피 봇 피해 0 **그리고** 감속된 프레임 0
  - A8 변위 경계·OBB·무적·2,000ms 잠금 (2차)
  - A9 화면 밖 사수 예고 진입 0
  - **A10 `context.bossPressure`가 켜진 창 안에서 신규 예고 진입 0.** 창 안의 발사는 창 이전에 진입한 예고분만 허용한다. E49는 `bossSpawnSec − 5.6s`부터 진입 0
  - A11 실기 p95 +2ms 이하, 셰이더 히치 ≤ 100ms, `gl.info.render.calls` +50 이하. **기록된 위험: 추정치는 +20~47이라(E34~E45가 같이 화면에 있으면 +47) 여유가 3뿐이다.** 0-10 실기 게이트에서 Track B와 신규 종이 섞인 Stage 4 구간으로 잰다. 넘으면 소품 슬롯 K를 3 → 2로 줄이는 것(−2)을 먼저 검토한다. 실기 없이는 "검증됨"으로 표기하지 않는다
  - A12 포트레이트 실화면에서 예고 3채널 중 2채널 이상 식별
- **측정 도구 고정 (A4·A6·A10)**
  - `gameplaySoak.js`로는 신규 종을 판정하지 않는다. 그 하네스는 bossPressure 창을 `sec >= 120 && sec < 150`으로 잡아 런타임과 다르고(`gameplaySoak.js:465`), 45프레임마다 레벨을 1 올리는 churn 모델이라(`:531-532`) XP와 레벨을 잴 수 없다. 이 하네스를 런타임 정의에 맞추는 작업은 별도 과제다.

  - 플레이어 봇은 **정지 봇과 원 카이팅 봇 두 종류**를 쓴다. 후퇴형(E47, E55)은 정지 봇에게 다가오지 않을 수 있어서 두 봇 모두에서 판정한다.
  - 시드는 **3개 이상**, 기준선은 **대체 전 같은 시드**, 측정 구간은 **0~240s**다.
