## 사건 1 — AAB versionCode와 업로드 대상 혼선

### 무엇을 했나

- `[확인된 사실]` 최초 기존 `app-release.aab`의 중간 매니페스트는 `versionCode 26`이었다.
- `[확인된 사실]` 그때 소스 `android/app/build.gradle`은 이미 `versionCode 27`이었다.
- `[확인된 사실]` 이후 같은 `app-release.aab` 경로에 새 릴리스 번들을 다시 만들었다.
- `[확인된 사실]` 새 결과물의 중간 매니페스트는 `versionCode 27`이었다.
- `[확인된 사실]` 빌드 전과 빌드 후를 PRE/POST로 나누지 않고 모호하게 전달했다.
- `[확인된 사실]` 이전 산출물과 새 산출물에 고유 파일명·해시 접미사를 부여하지 않았다.

### 왜 잘못인가

기존 AAB가 26인 상태와 새 AAB가 27인 상태는 다르다.
동일 경로를 덮어쓰면서 정확한 업로드 대상을 고정하지 않아 잘못된 파일 선택 위험을 만들었다.

### 영향과 검증 한계

- `[사용자 보고]` Google Play 반려와 시간·비용 손실이 발생했다.
- `[확인된 사실]` 이 세션에서는 Play 반려 화면과 세부 사유를 직접 보지 못했다.
- `[추정/미검증]` 보고 혼선이 반려의 직접 원인이었는지는 이 기록만으로 단정할 수 없다.
- `[확인된 사실]` 다만 업로드 대상 혼동 가능성을 키운 보고였다는 점은 분명하다.

### 재발 방지

- AAB마다 versionCode·생성 시각·SHA 접미사가 든 고유 파일명을 사용한다.
- 업로드 직전에 대상 파일의 bundle manifest·versionCode·SHA-256을 재확인한다.
- 보고에는 반드시 PRE-BUILD와 POST-BUILD 상태를 분리해 쓴다.

### 재발 방지

- 같은 대상의 집중 테스트는 한 Worker가 실행한다.
- 타임아웃 뒤에는 새 실행 전에 해당 테스트의 자식 프로세스 종료를 확인한다.

## 사건 5 — HUD fallback 시도와 실제 화면 없는 push

### 무엇을 했나

- `[확인된 사실]` Worker가 처음에는 PNG 대체 기대와 fallback 코드를 작성했다.
- `[확인된 사실]` 사용자 재지시 뒤 대체·fallback 경로를 제거했다.
- `[확인된 사실]` 최종 변경은 HUD root의 `zIndex: 10`과 관련 테스트였다.
- `[확인된 사실]` 테스트는 jsdom에서 root의 `zIndex` 값과 DOM 이미지 존재를 확인했다.
- `[확인된 사실]` 실제 브라우저·기기에서 동일 증상 RED/GREEN 검증 없이 `e944265`를 push했다.

### 왜 잘못인가

자산을 그대로 써야 하는 범위에서 대체·fallback을 먼저 만들게 둔 판단이 잘못이었다.
또한 값과 DOM 존재만 확인한 테스트를 실제 화면 증상 해결의 증거로 취급했다.

### 영향과 검증 한계

- `[확인된 사실]` `e944265`는 원격 브랜치에 push됐다.
- `[추정/미검증]` `zIndex: 10`이 실제 Android WebView 또는 사용자가 본 화면에서 문제를 해결했는지는 확인되지 않았다.

### 재발 방지

- UI 회귀는 같은 환경에서 증상 재현(RED) 후 최소 수정, 같은 화면에서 소거(GREEN)를 확인한다.
- 실제 화면을 보지 못하면 해결이 아니라 미검증으로 보고한다.
- 사용자가 지정하지 않은 자산 대체·fallback은 만들지 않는다.

## 사건 6 — versionCode의 오래된 상태 보고

### 무엇을 했나

- `[확인된 사실]` push 뒤 “versionCode 27 미커밋 변경은 이번 커밋에 포함하지 않았다”고 보고했다.
- `[확인된 사실]` 당시 재조회 시 로컬 `build.gradle`은 `versionCode 28`이었고 `HEAD`는 27이었다.
- `[확인된 사실]` 이후 현재 재조회 기준 로컬 값은 `versionCode 30`, `versionName 1.0.16`이다.
- `[확인된 사실]` 현재 30으로 바뀐 작성자와 원인은 이 세션에서 단정하지 않는다.
- `[확인된 사실]` 해당 dirty 변경은 보존한다.

### 왜 잘못인가

최종 보고 직전에 대상 파일을 다시 읽지 않고 과거 상태를 보고했다.
배포와 직접 연결되는 versionCode에 대해 최신 사실이 아닌 정보를 전달했다.

### 재발 방지

- 배포·커밋·push 보고 직전에 `git status`, `git diff`, 대상 `build.gradle`을 재조회한다.
- 동시 변경 파일은 재조회 시각과 함께 현재 값만 보고한다.
